# 计算机系统概论（六）：函数调用

> 本篇对应课件第六讲《C 语言的机器表示（三）》（课件标题为"80X86 汇编语言与 C 语言-3"）。上一篇讲了跳转，这一篇讲另一种改变控制流的机制：函数的调用与返回。它是整个"程序的机器表示"部分的核心，也是后面缓冲区溢出一讲的基础。

## 1. 先看三个问题

课件用一个递归的阶乘函数引出这一讲：

```c
long factorial(long n)
{
    long local_n = n;                       // 局部变量
    if (n <= 1)
        return 1;
    long result = n * factorial(n - 1);     // 递归调用
    return result;
}
```

- **问题 1：同一个局部变量的多个并存。** `factorial(5)` 调用 `factorial(4)`，再调用 `factorial(3)`……每一层都有一个叫 `local_n` 的局部变量，值各不相同。它们存在哪里？为什么不会互相覆盖？
- **问题 2：返回地址的定位。** `factorial(3)` 执行到 `factorial(n-1)` 时，CPU 跳到了 `factorial(2)` 的代码；等 `factorial(2)` 执行到 `return`，CPU 怎么知道要回到 `factorial(3)` 里那一行的**下一条指令**？
- **问题 3：参数的"接力"。** 每一层的参数 `n` 都要传给下一层，机器层面具体怎么完成？参数很多（超过 6 个）会怎么样？

这一讲的内容就是依次回答这三个问题。课件把函数调用要解决的事归为三类：

| 要解决的事 | 具体内容 |
|---|---|
| 控制转移（passing control） | 调用时转到被调用函数，返回时回到调用点的下一条指令 |
| 数据传递（passing data） | 函数参数与返回值 |
| 内存管理（memory management） | 调用时分配局部变量需要的空间，返回时释放 |

这些全部由机器指令来实现。

## 2. 程序栈

x86-64 的**程序栈**是内存中的一块区域，按"栈"（后进先出）的方式工作，有两个关键特征：

- 它从**高地址向低地址增长**，也就是说栈"往下"长；
- 寄存器 **`%rsp`** 存放**栈顶**的地址。

两条基本指令：

| 指令 | 动作 |
|---|---|
| `pushq Src` | 取得 `Src` 的值；`%rsp = %rsp - 8`；把值写入新的栈顶地址 `(%rsp)` |
| `popq Dest` | 读取栈顶 `(%rsp)` 处的数据；`%rsp = %rsp + 8`；把数据写入 `Dest` |

用数字走一遍。设 `%rsp = 0x108`，`%rax = 0x1234`：

```asm
pushq %rax        # %rsp ← 0x108 - 8 = 0x100；Mem[0x100] ← 0x1234
popq  %rbx        # %rbx ← Mem[0x100] = 0x1234；%rsp ← 0x100 + 8 = 0x108
```

所以 `pushq Src` 等价于 `subq $8,%rsp` 加 `movq Src,(%rsp)` 两条，`popq Dest` 等价于 `movq (%rsp),Dest` 加 `addq $8,%rsp`，只是合成了一条指令。注意 `pop` 之后，被弹出的数据（`0x1234`）仍然留在内存 `0x100` 里，只是栈顶指针移动了，它已经不属于栈的有效部分，下一次 `push` 就会把它覆盖。

**"从高地址向低地址增长"的直觉**：把栈想成倒着长的一摞盘子，栈底固定在高地址一侧，新放的东西放在更低的地址。第七讲会看到，进程的地址空间里栈在最上面向下长，堆在下面向上长，两者相向而行，中间留出空档，这样两边都能灵活增长。这也是为什么 `push` 要让 `%rsp` 减小。

## 3. 控制转移：`call` 与 `ret`

用栈就能完成函数调用与返回：

- **`call label`**：把**返回地址**压入栈，然后跳转到 `label`。返回地址就是 `call` 指令**下一条指令**的地址；
- **`ret`**：从栈顶弹出返回地址，跳转到那里。

换一种说法：`call label` 相当于 `pushq <返回地址>` 再 `jmp label`；`ret` 相当于 `popq %rip`。`%rip` 就是第五讲讲过的程序计数器，存放下一条要执行的指令的地址，所以"弹出到 `%rip`"就是"跳转"。**返回地址之所以要存在栈里，是因为调用可以嵌套**：函数 A 调 B，B 再调 C，A、B 各自的返回地址都要保存，而且返回时先用 C 的、再用 B 的，正好是后进先出。

课件用这个例子：

```text
0000000000400540 <multstore>:
  400540: push   %rbx            # 保存 %rbx
  400541: mov    %rdx,%rbx       # 保存 dest
  400544: callq  400550 <mult2>  # mult2(x,y)
  400549: mov    %rax,(%rbx)     # 把结果存入 dest
  40054c: pop    %rbx            # 恢复 %rbx
  40054d: retq

0000000000400550 <mult2>:
  400550: mov    %rdi,%rax       # a
  400553: imul   %rsi,%rax       # a*b
  400557: retq
```

设 `callq` 执行前 `%rsp = 0x120`，`%rip = 0x400544`。三步过程如下图：

![](/obsidian-assets/614476c455369424.png)

- 执行 `callq 400550`：`%rsp` 减 8 变成 `0x118`，把 `0x400549`（`call` 的下一条指令地址）写进 `0x118`，`%rip` 改成 `0x400550`；
- `mult2` 执行完，遇到 `retq`：从 `0x118` 取出 `0x400549` 放进 `%rip`，`%rsp` 加 8 变回 `0x120`；
- 于是 CPU 回到 `0x400549`，继续执行 `mov %rax,(%rbx)`。

**这回答了问题 2**：返回地址由 `call` 自动压入栈中，`ret` 自动弹出；因为栈是后进先出的，嵌套调用时最后被调用的函数先返回，恰好用到最后压入的返回地址，层层对应，不会错乱。

## 4. 数据传递：参数与返回值

x86-64 规定：

- **前六个参数**依次放在寄存器 `%rdi`、`%rsi`、`%rdx`、`%rcx`、`%r8`、`%r9` 中；
- **第七个及以后**的参数放在栈上，**从右往左压栈**（也就是第七个参数在栈中离栈顶最近）；栈空间**仅在需要时才分配**；
- **返回值**放在 `%rax`。

先用一个 7 个参数的函数看一下"第七个参数在栈上"是什么样子（用 gcc 编译得到）：

```c
long add7(long a,long b,long c,long d,long e,long f,long g)
{ return a+b+c+d+e+f+g; }
long call7() { return add7(1,2,3,4,5,6,7); }
```

```asm
call7:
    pushq  $7                # 第 7 个参数 g = 7，压栈
    movl   $6, %r9d          # 第 6 个参数 f
    movl   $5, %r8d          # e
    movl   $4, %ecx          # d
    movl   $3, %edx          # c
    movl   $2, %esi          # b
    movl   $1, %edi          # a
    call   add7              # 压入返回地址，跳转
    addq   $8, %rsp          # 调用返回后，调用者自己把那个参数从栈上"弹掉"
    ret

add7:
    addq   %rsi, %rdi        # a+b
    addq   %rdx, %rdi        # +c
    addq   %rcx, %rdi        # +d
    addq   %r8,  %rdi        # +e
    leaq   (%rdi,%r9), %rax  # +f
    addq   8(%rsp), %rax     # +g：g 就在 8(%rsp)
    ret
```

`add7` 刚进入时，`(%rsp)` 是返回地址，`call` 刚压进去的；紧挨着的 `8(%rsp)` 就是调用者之前压入的 `g`。这与刚才 `call` 的行为是吻合的：`pushq $7` 先压，`call` 后压返回地址，所以返回地址在更低的地址（离栈顶更近），参数在它上面。栈上的参数由**调用者**负责释放（`addq $8,%rsp`），被调用者不管。

对照上面的例子：`multstore(x, y, dest)` 中 `x` 在 `%rdi`、`y` 在 `%rsi`、`dest` 在 `%rdx`；它调用 `mult2(x, y)` 时，参数恰好已经在 `%rdi`、`%rsi` 里，无需搬动，`mult2` 把结果放在 `%rax` 返回，回到 `multstore` 之后 `t` 就在 `%rax`。

**这回答了问题 3**：参数通过寄存器"接力"，参数多于 6 个时多出的部分通过栈传递。

## 5. 内存管理：栈帧

### 为什么需要栈帧

C、Pascal、Java 这类基于栈的语言都**支持递归**，这意味着：

- 函数的代码是**可重入**的：同一个函数可以同时有多个**实例**在运行；
- 因此每个实例都需要一块自己的存储区域，用来放它的**参数、局部变量、返回地址**；
- 这块区域的生命周期是有限的：**从被调用开始，到返回结束**，并且（一般情况下）**被调用者先于调用者返回**。这正是"后进先出"，与栈的工作方式完全吻合。

每个函数实例在栈中维护一个**栈帧（stack frame）**，存放的内容是局部变量、返回地址和临时空间。

### 栈帧的分配与释放

进入函数后先"分配"栈帧（set-up 代码），返回前"释放"（finish 代码）。寄存器 `%rbp` 可以作为**帧指针**，指向当前栈帧的起始位置（用 `-fno-omit-frame-pointer` 编译时才使用，否则这个寄存器会被当作普通寄存器）；`%rsp` 始终是栈顶指针。

课件用 `yoo → who → amI → amI`（`amI` 自己递归了一次）这个调用链，动画展示了栈随着调用不断生长、返回时不断收缩的过程，最终效果如下：

![](/obsidian-assets/2ca46316a544ef13.png)

右侧就是栈：最底下是 `yoo` 的栈帧，每调用一层，往下压入一帧；`%rsp` 始终指向最新的那一帧的顶。**这回答了问题 1**：每次调用 `factorial` 都有自己的栈帧，各层的 `local_n` 存在各自的栈帧里，地址不同，所以不会互相覆盖。

### x86-64/Linux 下的栈帧

![](/obsidian-assets/e79cc7c5df43f3c5.png)

按从栈底（高地址）到栈顶（低地址）的顺序，一个栈帧中包含：

1. **调用者的栈帧**中与本函数相关的部分：**第七个及以后的参数**，以及（在它们之下）由 `call` 指令存入的**返回地址**；
2. （可选）**帧指针**位置：保存**调用者的 `%rbp` 原值**，`%rbp` 指向这里；
3. **被保存的寄存器值**（本函数要用被调用者保存的寄存器时，先保存它们原来的值）；
4. **局部变量**：因为通用寄存器数量有限，放不下的局部变量，或者需要取地址的局部变量，放在栈帧里；
5. **子函数的参数**（第七个及以后），在栈顶 `%rsp` 附近，为调用别的函数提前准备。

### 以 `call_incr2` 看一个栈帧的一生

把一个栈帧的建立、使用、释放连起来看，用第 7 节 `call_incr2` 的汇编（见下文）。设进入时 `%rsp = S`，栈内容从高到低依次是：

| 执行到 | `%rsp` | 栈中新增的内容（从高地址到低地址） |
|---|---|---|
| 刚进入 `call_incr2`（`call` 已压入返回地址） | `S` | 返回地址（`call_incr2` 的调用者那边的下一条指令） |
| `pushq %rbx` | `S-8` | 保存的 `%rbx` 原值 |
| `subq $16,%rsp` | `S-24` | 16 字节局部空间（其中存 `v1`） |
| `call incr` | `S-32` | `incr` 的返回地址 |
| `incr` 返回后 | `S-24` | 返回地址已弹出 |
| `addq $16,%rsp`、`popq %rbx`、`ret` | `S` → `S+8` | 逐项释放，回到进入前 |

建立栈帧就是几次 `push` 和一次 `sub`，**释放就是反方向的 `add`、`pop`**，进入和退出的操作一一对称，这样 `ret` 执行时栈顶一定又是返回地址。

**帧指针 `%rbp`** 在需要时才用，作用是给栈帧里的数据一个**不随 `%rsp` 变化的参照点**。例如（`-fno-omit-frame-pointer`）：

```asm
g:
    pushq  %rbp               # 保存调用者的 %rbp
    movq   %rsp, %rbp         # %rbp 指向这里，此后不变
    subq   $16, %rsp          # 分配局部空间，%rsp 继续下移
    movq   %rdi, -16(%rbp)    # 局部变量用 %rbp 加固定偏移访问
    ...
    call   who
    leave                     # 等价于 movq %rbp,%rsp 与 popq %rbp：一步释放栈帧
    ret
```

`leave` 把 `%rsp` 直接设回 `%rbp`（栈帧里的所有东西一下子都释放了），再弹出旧的 `%rbp`。当栈帧大小在运行时才确定时（见第八篇的变长数组），`%rsp` 无法再当作稳定参照，必须用 `%rbp`。

### x86-64 栈帧操作的特点

- **一次性分配整个栈帧**：函数开头把 `%rsp` 减去栈帧大小，之后对栈帧内容的访问都基于 `%rsp`；
- **可以延迟分配**：不必一进函数就分配；
- **可以直接访问 `%rsp` 以下 128 字节**的栈空间（red zone，后面细讲）；
- **释放很简单**：`%rsp` 直接加回栈帧大小。

## 6. 例子：调用 `incr`

```c
long incr(long *p, long val) {
    long x = *p;
    long y = x + val;
    *p = y;
    return x;
}
```

```asm
incr:
    movq  (%rdi), %rax     # x = *p
    addq  %rax, %rsi       # y = x + val
    movq  %rsi, (%rdi)     # *p = y
    ret
```

寄存器用途：`%rdi` 是 `p`，`%rsi` 是 `val`（之后复用为 `y`），`%rax` 是 `x`（同时作为返回值）。

调用方：

```c
long call_incr() {
    long v1 = 15213;
    long v2 = incr(&v1, 3000);
    return v1 + v2;
}
```

```asm
call_incr:
    subq   $16, %rsp          # 分配 16 字节栈帧
    movq   $15213, 8(%rsp)    # v1 = 15213，放在栈上
    movl   $3000, %esi        # 第二个参数 val = 3000
    leaq   8(%rsp), %rdi      # 第一个参数 &v1
    call   incr
    addq   8(%rsp), %rax      # %rax = v2 + v1
    addq   $16, %rsp          # 释放栈帧
    ret
```

这里的细节值得逐条体会：

1. 进入 `call_incr` 时，栈顶（`%rsp` 指向的位置）就是返回地址；
2. `subq $16, %rsp` 分配 16 个字节，其中 `8(%rsp)` 存放 `v1`，另外 8 个字节暂时没用（Unused）。这个"没用"的 8 字节是为了**栈对齐**：x86-64 规定在执行 `call` 时，`%rsp` 必须是 16 的倍数（某些指令要求 16 字节对齐的内存），而进入一个函数时，`call` 刚压入 8 字节返回地址，所以栈顶地址比 16 的倍数少 8；函数分配的栈空间需要凑出合适的大小，把 `%rsp` 重新对齐。（这里是课件和教材里的汇编。较新版本的 gcc 通常会写成 `subq $24,%rsp`，并把 `v1` 放在 `8(%rsp)`，也是出于这条对齐规则，细节随版本和选项而异，不影响理解。）
3. **为什么 `v1` 必须放在栈上？** 因为 `incr(&v1, ...)` 要取 `v1` 的地址，寄存器没有地址，所以必须放在内存里，而局部变量的内存就在栈帧里，`leaq 8(%rsp), %rdi` 就是在计算 `&v1`；
4. `movl $3000, %esi` 写的是 32 位寄存器，会把 `%rsi` 高 32 位清零，所以实际上整个 `%rsi` 都是 3000；
5. `call incr` 压入返回地址，`incr` 执行完回来；`incr` 把 `*p` 改成了 `15213 + 3000 = 18213`，并返回旧值 15213，所以 `%rax = 15213`（`v2`）、栈上 `v1 = 18213`，最终返回 `15213 + 18213 = 33426`；
6. 结尾 `addq $16, %rsp` 释放栈帧，此时栈顶又是返回地址，`ret` 就能返回到 `call_incr` 的调用者。

![](/obsidian-assets/c9eeb6fc7fbfd243.png)

上图是课件给出的栈状态：左上是调用前（栈顶只有返回地址），左下是执行完前两条指令后（多出 `v1 = 15213` 与一个 Unused 的槽）。

## 7. 寄存器使用惯例

寄存器是整个处理器共享的，**只有一组**。如果 `yoo` 调用 `who`，二者都用 `%rdx`，就会出问题：

```asm
yoo:
    movq  $15213, %rdx
    call  who
    addq  %rdx, %rax     # yoo 以为 %rdx 还是 15213
    ret

who:
    subq  $18213, %rdx   # who 把 %rdx 改掉了
    ret
```

`yoo` 是**调用者（caller）**，`who` 是**被调用者（callee）**。两者必须在寄存器的使用上"达成默契"，课件给出的是**使用惯例**：把通用寄存器分成两类。

| 类型 | 谁负责保存 | 做法 |
|---|---|---|
| **调用者保存**（被调用者可破坏，call clobbered） | 调用者 | 调用子函数**之前**，调用者把这些寄存器的内容保存在自己的栈帧里，调用之后再恢复 |
| **被调用者保存** | 被调用者 | 被调用者在使用这些寄存器**之前**，先把原值保存到自己的栈帧里，**退出之前**恢复 |

x86-64 的具体分类：

| 寄存器 | 用途/类型 |
|---|---|
| `%rax` | 返回值 |
| `%rdi, %rsi, %rdx, %rcx, %r8, %r9` | 第 1–6 个参数（其中 `%rdx`、`%rcx` 被调用者可破坏） |
| `%r10, %r11` | 调用者保存（被调用者可破坏） |
| `%rbx, %r12, %r13, %r14, %r15` | **被调用者保存** |
| `%rbp` | 被调用者保存（也可选作帧指针） |
| `%rsp` | 栈顶指针 |

### 调用者保存的例子

先看"谁来保存"的两种可能。以 `yoo` 为例，它在调用 `who` 前后都要用 `%rdx`：

```asm
# 办法一：调用者保存——yoo 在调用 who 之前自己把 %rdx 存起来
yoo:
    movq  $15213, %rdx
    pushq %rdx            # 保存
    call  who
    popq  %rdx            # 恢复
    addq  %rdx, %rax
    ret
```

办法二是让 `who` 在用 `%rdx` 之前先 `pushq %rdx`，返回前 `popq %rdx`，调用者就什么都不用做（被调用者保存）。两种办法选哪一种，就是**约定**：对每个寄存器规定好是哪一方负责。

约定的好处是，**调用者可以放心地让一部分值留在"被调用者保存"的寄存器里跨过调用，不必每次手动存取；被调用者可以随意使用"调用者保存"的寄存器，不用先保存**，各取所需。习惯上，**要在调用之后继续用的值**放在被调用者保存的寄存器（如 `%rbx`）里；**只是临时算一下的值**用调用者保存的寄存器（如 `%r10`、`%r11`）就行。

### 被调用者保存的例子

```c
long call_incr2(long x) {
    long v1 = 15213;
    long v2 = incr(&v1, 3000);
    return x + v2;       // 上一个版本是 v1 + v2
}
```

```asm
call_incr2:
    pushq  %rbx              # 保存 %rbx 的原值（被调用者保存）
    subq   $16, %rsp
    movq   %rdi, %rbx        # 把参数 x 放进 %rbx
    movq   $15213, 8(%rsp)
    movl   $3000, %esi
    leaq   8(%rsp), %rdi
    call   incr
    addq   %rbx, %rax        # x + v2
    addq   $16, %rsp
    popq   %rbx              # 恢复 %rbx
    ret
```

`x` 是通过 `%rdi` 传进来的，但 `%rdi` 是参数寄存器，`call incr` 之前又要拿它传 `&v1`，所以 `x` 必须挪到别处，才能在调用之后还能使用。这里选了**被调用者保存**的 `%rbx`：因为 `incr` 要遵守约定，如果用 `%rbx` 就会保存、恢复它，所以 `call incr` 之后 `%rbx` 里的 `x` 依然有效。**代价**是 `call_incr2` 自己得在入口 `pushq %rbx`、出口 `popq %rbx`，替它的调用者保存原值。栈状态：入口时栈顶是返回地址，`pushq %rbx` 后多了一项 "Saved %rbx"，`subq $16` 后多了局部变量的空间。

## 8. 递归调用

```c
/* 递归地统计 x 的二进制表示中 1 的个数 */
long pcount_r(unsigned long x)
{
    if (x == 0)
        return 0;
    else
        return (x & 1) + pcount_r(x >> 1);
}
```

`gcc -Og` 的结果：

```asm
pcount_r:
    movl   $0, %eax          # 先把返回值置 0（x == 0 时直接用）
    testq  %rdi, %rdi
    je     .L6               # x == 0，直接返回 0
    pushq  %rbx              # 保存 %rbx
    movq   %rdi, %rbx
    andl   $1, %ebx          # %rbx = x & 1，要跨调用保存，所以放在被调用者保存的 %rbx 里
    shrq   %rdi              # x >> 1，作为递归调用的参数
    call   pcount_r          # 递归调用
    addq   %rbx, %rax        # (x & 1) + 递归结果
    popq   %rbx              # 恢复 %rbx
.L6:
    ret
```

分析各寄存器的用途：

| 寄存器 | 用途 | 类型 |
|---|---|---|
| `%rdi` | 进入时是参数 `x`，递归前被改为 `x >> 1` | 参数 |
| `%rbx` | `x & 1`，递归返回之后还要用 | 被调用者保存 |
| `%rax` | 返回值 | 返回值 |

**递归的退出条件**由开头的 `testq / je` 处理：`x == 0` 时 `%rax` 已经是 0，直接 `ret`。**递归的"保存与恢复"**由 `pushq %rbx` / `popq %rbx` 完成：每一层把调用者（上一层）的 `%rbx` 压栈，用自己的 `%rbx` 存 `x & 1`，递归返回后再弹出恢复。

以 `x = 5`（`101₂`）为例，调用链和返回过程是：

| 层 | `x` | 该层的 `%rbx`（`x & 1`） | 返回值 |
|---|---|---|---|
| `pcount_r(5)` | 101₂ | 1 | `1 + pcount_r(2)` |
| `pcount_r(2)` | 10₂ | 0 | `0 + pcount_r(1)` |
| `pcount_r(1)` | 1₂ | 1 | `1 + pcount_r(0)` |
| `pcount_r(0)` | 0 | — | 0 |

返回时逐层向上累加：$0\to1\to1\to2$，结果为 2，正确。

可以把整个过程中栈的内容画出来。设 `main` 调用 `pcount_r(5)` 时 `%rbx` 里是某个值 $R_0$，`A` 表示"`pcount_r` 里 `call pcount_r` 的下一条指令地址"（每次递归返回的都是这里）。栈由高地址到低地址，走到最深处 `pcount_r(0)` 时是：

| 栈中内容（高 → 低） | 是谁压的 |
|---|---|
| 返回 `main` 的地址 | `main` 调用 `pcount_r(5)` 时的 `call` |
| $R_0$（`main` 的 `%rbx`） | `pcount_r(5)` 的 `pushq %rbx` |
| `A` | `pcount_r(5)` 调用 `pcount_r(2)` 的 `call` |
| 1（`pcount_r(5)` 的 `x&1`） | `pcount_r(2)` 的 `pushq %rbx` |
| `A` | `pcount_r(2)` 调用 `pcount_r(1)` 的 `call` |
| 0（`pcount_r(2)` 的 `x&1`） | `pcount_r(1)` 的 `pushq %rbx` |
| `A` | `pcount_r(1)` 调用 `pcount_r(0)` 的 `call` |

此时 `%rbx = 1`（`pcount_r(1)` 的 `x&1`），`pcount_r(0)` 发现 `x == 0`，不碰 `%rbx`，直接 `ret`。返回过程中每一层做同样两步：`addq %rbx,%rax` 把本层的 `x&1` 加进结果，再 `popq %rbx` 把上一层的 `%rbx` 取回来，于是上一层继续运算时，`%rbx` 里又是它自己的 `x&1`。可以看出：**每一层的栈帧中"保存的 `%rbx`"装的是上一层的值，各层的值依次排在栈里，互不覆盖**，这就是递归能够正确工作的原因，也是对第 1 节问题 1 的一个具体回答。

## 9. 几个值得细想的现象

### 9.1 局部变量不一定在栈上：red zone

```c
void swap_a(long *xp, long *yp) {
    volatile long loc[2];       // volatile：强制每次真正访问内存
    loc[0] = *xp;
    loc[1] = *yp;
    *xp = loc[1];
    *yp = loc[0];
}
```

```asm
swap_a:
    movq  (%rdi), %rax
    movq  %rax, -24(%rsp)     # loc[0]
    movq  (%rsi), %rax
    movq  %rax, -16(%rsp)     # loc[1]
    movq  -16(%rsp), %rax
    movq  %rax, (%rdi)
    movq  -24(%rsp), %rax
    movq  %rax, (%rsi)
    ret
```

先说明两个词：`volatile` 告诉编译器"这个变量可能在别处被改，每次读写都必须真的访问内存"，所以 `loc` 不会被编译器优化到寄存器里；**叶子函数**指的是不再调用其他函数的函数。

`loc` 是个局部数组，用了栈空间，但**整个过程中根本没有修改 `%rsp`**，直接用 `-24(%rsp)`、`-16(%rsp)` 访问了 `%rsp` 之下的内存。原因是 x86-64 规定了 **red zone**：**`%rsp` 之下 128 字节的区域是被保留的**，不会被信号处理、中断等异常流程所破坏，所以**不再调用其他函数的"叶子"函数**可以放心用它，省掉一次栈指针的减法与加法。（这里的"不会被破坏"说的是：栈顶以下的内存，系统在处理信号、中断时会避开这 128 字节再使用栈；如果函数里还要 `call` 别的函数，`call` 压入的返回地址和被调函数的栈帧就会占用 `%rsp` 以下的区域，red zone 就不能用了，所以只有叶子函数能用。）

![](/obsidian-assets/1e251e1a4e52d75d.png)

课件总结局部变量的去处只有三种：**被优化掉**、**放在寄存器**、**放在运行栈**。

### 9.2 没有分配栈帧的函数

```c
long scount = 0;
void swap_ele_se(long a[], int i)
{
    swap(&a[i], &a[i+1]);
    scount++;
}
```

```asm
swap_ele_se:
    movslq %esi, %rsi              # i 符号扩展成 64 位
    leaq   (%rdi,%rsi,8), %rdi     # &a[i]
    leaq   8(%rdi), %rsi           # &a[i+1]
    call   swap
    incq   scount(%rip)            # scount++
    ret
```

课件问：这个函数**没有分配栈帧**，为什么？因为它**不需要**：没有需要放进栈里的局部变量，没有要保存的被调用者保存寄存器，传给 `swap` 的参数都在寄存器里，用得上的只有 `call` 自动压入的返回地址。栈帧是"按需"的，不是每个函数都有。

顺便看一个新的寻址形式：`scount(%rip)` 叫 **RIP 相对寻址**，有效地址 = `%rip`（即下一条指令的地址）+ 一个位移量，这样全局变量的访问不依赖程序被装入的具体位置。

### 9.3 用 `jmp` 调用：尾调用

```c
void swap_ele(long a[], int i)
{
    swap(&a[i], &a[i+1]);       // 最后一件事就是调用 swap
}
```

```asm
swap_ele:
    movslq %esi, %rsi
    leaq   (%rdi,%rsi,8), %rdi
    leaq   8(%rdi), %rsi
    jmp    swap                 # 注意：是 jmp，不是 call
```

课件问：为什么用 `jmp` 而不是 `call`？`swap` 将会返回到哪儿？答案是：`swap_ele` 的最后一件事就是调用 `swap`，调用完不需要再做任何事。此时栈顶仍然是**调用 `swap_ele` 的那个函数**压入的返回地址，直接 `jmp swap`，那么 `swap` 的 `ret` 会弹出这个地址，**直接返回到 `swap_ele` 的调用者**。这样既省了一次压栈、弹栈，也省了一个栈帧，这就是**尾调用优化**。对比一下：若写成 `call swap` 再 `ret`，`swap` 返回到 `swap_ele`，`swap_ele` 再 `ret` 返回到它的调用者，要多走一步；改成 `jmp swap` 后，`swap_ele` 的"身份"被 `swap` 直接接替了，对调用者来说，仿佛它调用的就是 `swap`。这在递归函数里意义更大，尾递归可以做到栈不增长。

## 10. x86-32 的函数调用（对照）

用 `-m32` 编译（需要安装 `gcc-multilib`）可以看到旧的 32 位约定，它与 x86-64 的差别主要是：**参数全部通过栈传递**，`%ebp` 作为帧指针被固定使用。

```c
int zip1 = 15213, zip2 = 91125;
void call_swap() { swap(&zip1, &zip2); }
```

```asm
call_swap:
    pushl  $zip2          # 参数从右往左压栈
    pushl  $zip1
    call   swap
```

被调用者先建立栈帧：

```asm
swap:
    pushl  %ebp            # 保存调用者的帧指针
    movl   %esp, %ebp      # %ebp 指向当前栈帧起点
    pushl  %ebx            # 保存被调用者保存的寄存器
    movl   12(%ebp), %ecx  # yp
    movl   8(%ebp), %edx   # xp
    ...                    # 函数主体
    movl   -4(%ebp), %ebx  # 恢复 %ebx
    movl   %ebp, %esp      # 释放栈帧（x86 的 leave 指令等价于这两步）
    popl   %ebp
    ret
```

栈帧里的偏移（相对 `%ebp`）是：`12` 是 `yp`，`8` 是 `xp`，`4` 是返回地址，`0` 是保存的旧 `%ebp`，`-4` 是保存的旧 `%ebx`。通过 `%ebp` 加固定偏移就可以稳定地访问参数和局部变量，不受 `%esp` 变化的影响。

![](/obsidian-assets/d6af4b8477d2af50.png)

观察 `swap` 的整个过程可以验证寄存器约定：**`%ebx` 被 `swap` 保存并恢复，而 `%eax`、`%ecx`、`%edx` 没有**，因为前者是被调用者保存的，后三者是调用者保存的。

## 11. 一道有意思的题：打破调用与返回的顺序

一般情况下"返回的顺序与调用的顺序相反"，但是只要理解了运行栈，就可以写出打破这个惯例的代码。课件给了一对 x86-32 函数 `GET` 与 `SET`：`GET` 的唯一参数是一个内存块地址，用来保存当前处理器与栈的信息；`SET` 的唯一参数也是这个内存块地址，用来恢复 `GET` 保存的状态。

```asm
GET:
    movl  4(%esp), %eax          # (A)
    ...                          # 保存各寄存器
    movl  %edi, 20(%eax)
    movl  %esi, 24(%eax)
    movl  %ebp, 28(%eax)
    movl  %ebx, 36(%eax)
    movl  %edx, 40(%eax)
    movl  %ecx, 44(%eax)
    movl  $1, 48(%eax)
    movl  (%esp), %ecx           # (B)
    movl  %ecx, 60(%eax)
    leal  4(%esp), %ecx          # (C)
    movl  %ecx, 72(%eax)
    movl  44(%eax), %ecx
    movl  $0, %eax
    ret

SET:
    movl  4(%esp), %eax
    ...                          # 恢复各寄存器
    movl  20(%eax), %edi
    movl  24(%eax), %esi
    movl  28(%eax), %ebp
    movl  36(%eax), %ebx
    movl  40(%eax), %edx
    movl  44(%eax), %ecx
    movl  ____ (%eax), %esp      # (D)
    pushl 60(%eax)               # (E)
    movl  48(%eax), %eax
    ret
```

先说明这对函数做什么。`GET(buf)` 把"此刻的处理器状态"（寄存器、栈指针、返回地址）存进内存块 `buf`；`SET(buf)` 把这些状态从 `buf` 里**全部恢复**。这和 C 标准库的 `setjmp` / `longjmp` 是一回事，用起来是这样的：

```c
if (GET(buf) == 0) {
    /* GET 第一次返回，返回值是 0：走这里 */
    ...
    SET(buf);               /* 恢复现场：程序"回到" GET 刚返回的地方 */
} else {
    /* 因 SET 而"再次从 GET 返回"，这次返回值是 1：走这里 */
}
```

`SET` 执行后，程序不会回到 `SET` 的调用点，而是**回到 `GET` 当初返回的那个位置**，好像 `GET` 又返回了一次，只是返回值变了。它违反了"每个函数返回一次，且按调用的逆序返回"的惯例，但依然只靠栈和寄存器的操作实现。

下面逐条分析。内存块里保存的东西按偏移存放：各寄存器分别在 20、24、28、36、40、44，常数 1 在 48，**`GET` 的返回地址在 60，`GET` 返回后调用者应有的栈指针在 72**。

- **(A)**：`x86-32` 里参数在栈上，进入函数时 `(%esp)` 是返回地址，`4(%esp)` 是第一个参数。所以执行后 **`%eax` 里是传入的内存块地址**；
- **(B)**：`(%esp)` 是 `GET` 的返回地址，所以执行后 **`%ecx` 里是 `GET` 的返回地址**（也就是调用 `GET` 的那条 `call` 的下一条指令的地址），随后被存到偏移 60；
- **(C)**：`leal 4(%esp), %ecx` 计算的是 `%esp + 4`，也就是**`GET` 返回之后，调用者那边 `%esp` 应有的值**（`ret` 会弹掉返回地址），它被存到偏移 72，作为"保存的栈指针"；
- **(D)**：应填 **`72`**，把 `%esp` 恢复为 `GET` 时保存的栈指针；
- **(E)**：`pushl 60(%eax)` 把保存的"返回地址"压入刚刚恢复的栈，使得接下来的 `ret` 弹出的就是它，于是**控制流直接跳到 `GET` 返回点之后**。

把 `SET` 最后几条指令连起来看：`movl 72(%eax),%esp` 先把 `%esp` 恢复成 `GET` 返回后调用者那边的栈顶；`pushl 60(%eax)` 再把 `GET` 的返回地址压在这个栈顶上，这就**伪造**出了一个"刚被 `call GET` 压入返回地址"的栈；最后 `movl 48(%eax),%eax` 把返回值设为 1，`ret` 弹出刚压的地址，于是跳到那里。

因此，**`SET` 的"返回地址"并不是调用 `SET` 的位置，而是 `GET` 当时保存的返回地址；它的返回值是 `1`**（`movl 48(%eax), %eax`，而偏移 48 是 `GET` 里存进去的常量 `$1`）。效果就是：`GET` 第一次返回时返回值是 0；之后任何时候调用 `SET`，程序会**再次"从 `GET` 返回"**，这次返回值是 1。这与 C 标准库里 `setjmp` / `longjmp` 的行为相同，保存并恢复一份寄存器与栈的快照，思路也与后面会遇到的上下文切换相通。

## 12. 关于"定位"

函数调用里还有几类"定位"问题：

- **静态函数入口地址**：同一个文件内的 `static` 函数，调用它的 `call` 指令机器码是 `e8`，后面跟的是一个 **32 位的相对偏移**，目标地址 = 下一条指令地址 + 偏移，这个偏移在汇编阶段就能算出来；而**非静态（外部）函数**的入口地址，在编译时并不知道，偏移处先留空，需要**链接器**在链接时填上；
- **函数返回地址**：`call` 压栈、`ret` 弹栈，运行时才确定；
- **局部变量**：被优化掉、放进寄存器、或放在运行栈（上一节讲的三种去处）。

## 小结

1. 函数调用靠**栈**来实现：`call` 把返回地址压栈并跳转，`ret` 弹出并跳回；栈从高地址向低地址增长，`%rsp` 指向栈顶。
2. x86-64 的约定：前六个参数放 `%rdi, %rsi, %rdx, %rcx, %r8, %r9`，多于六个的从右往左压栈，返回值放 `%rax`。
3. 每个函数实例有一个**栈帧**，存放局部变量、保存的寄存器、返回地址等；调用时分配，返回时释放，所以递归时各层的局部变量互不干扰。
4. 寄存器是共享的，所以有**使用惯例**：`%rbx, %rbp, %r12–%r15` 由**被调用者保存**，其余（`%r10`、`%r11` 以及参数寄存器）由调用者保存。
5. x86-64 允许叶子函数使用 `%rsp` 以下 128 字节的 **red zone**；最后一步是调用的函数可以用 `jmp` 做**尾调用**；不需要的函数完全可以没有栈帧。
6. 理解了栈，就能理解为什么栈上的数据一旦被越界写入，就可能改写**返回地址**，这正是下一篇要讲的缓冲区溢出。
