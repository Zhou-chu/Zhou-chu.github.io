# 计算机系统概论（七）：内存布局与缓冲区溢出

> 本篇对应课件第七讲（课件标题为"80X86 汇编语言与 C 语言-6"）。上一篇讲了函数调用时栈上放了什么，这一篇回答一个自然的问题：如果往栈上的数组里写入超过它容量的数据，会发生什么？先用一节把进程的整体内存布局讲清楚，再进入缓冲区溢出。

## 1. Linux 进程的内存布局

### 1.1 一张图

x86-64 下，一个 Linux 进程看到的是一块**虚拟地址空间**。用户态可用的地址范围大约是 $2^{47}$ 字节，最高地址是 `0x00007FFFFFFFFFFF`。这块空间从低到高大致分成下面几个区域：

![](/obsidian-assets/3fe2196cfdff2a1f.png)

- **Text（代码段）**：存放机器指令，只读。可执行文件被加载时，代码段一般从 `0x400000` 附近开始。
- **Data（数据段）**：存放**静态分配**的数据，即全局变量、`static` 变量、字符串常量。它们的大小在编译、链接时就已经确定，程序一启动就存在。
- **Heap（堆）**：**运行时按需分配**，通过 `malloc`、`calloc`、`new` 等得到。堆从低地址向高地址增长。
- **Shared Libraries（共享库）**：`libc` 等动态库被映射到这里，位于地址空间的中部。
- **Stack（运行栈）**：存放局部变量、返回地址等（上一讲的内容）。栈顶在最高地址附近，**向低地址增长**，默认最大 8 MB。

要点是：堆向上长、栈向下长，中间留出一大片空洞。课件里 Heap 与 Stack 之间还夹着共享库，后面的例子会看到这一点。

### 1.2 用一段程序验证

课件给了一个分配各种内存的例子：

```c
char big_array[1L << 24];     /* 16 MB */
char huge_array[1L << 31];    /* 2 GB  */
int global = 0;
int useless() { return 0; }

int main()
{
    void *p1, *p2, *p3, *p4;
    int local = 0;
    p1 = malloc(1L << 28);    /* 256 MB */
    p2 = malloc(1L << 8);     /* 256 B  */
    p3 = malloc(1L << 32);    /* 4 GB   */
    p4 = malloc(1L << 8);     /* 256 B  */
    /* ... 打印各变量的地址 ... */
}
```

课件给出的一次运行结果是：

| 对象 | 地址 | 所在区域 |
| --- | --- | --- |
| `local` | `0x00007ffe4d3be87c` | 栈（最高端） |
| `p1`（256 MB） | `0x00007f7262a1e010` | 共享库一带（mmap 区） |
| `p3`（4 GB） | `0x00007f7162a1d010` | 共享库一带（mmap 区） |
| `p4`（256 B） | `0x000000008359d120` | 堆 |
| `p2`（256 B） | `0x000000008359d010` | 堆 |
| `big_array` | `0x0000000080601060` | 数据段 |
| `huge_array` | `0x0000000000601060` | 数据段 |
| `main()` | `0x000000000040060c` | 代码段 |
| `useless()` | `0x0000000000400590` | 代码段 |

这些数字可以逐条解释，这样就不是死记：

1. **代码在最低处**：`main`、`useless` 都在 `0x4005xx`，说明代码段从 `0x400000` 起；全局数组在 `0x601060`，紧跟其后。
2. **`big_array` 与 `huge_array` 相差正好 2 GB**：`0x80601060 − 0x00601060 = 0x80000000 = 2^31`。`huge_array` 先声明、先放置，占满 2 GB 之后才轮到 `big_array`，所以后者的地址恰好是前者加上 `huge_array` 的大小。
3. **小块与大块的 `malloc` 走的不是同一条路**：`p2`、`p4` 是 256 字节的小块，从**堆**里取，地址都在 `0x8359d...`，且 `p4 − p2 = 0x110 = 272`，即 256 字节再加上 16 字节的块头（管理信息）；`p1`、`p3` 是 256 MB 与 4 GB 的大块，`malloc` 直接用 `mmap` 向系统要一块独立的映射，地址落在共享库附近的 `0x7f..` 一带。
4. **mmap 区向低地址分配**：`p3` 比 `p1` 后分配，地址反而更小。`p1 − p3 = 0x100001000 = 4 GB + 4 KB`，正好等于 `p3` 这块映射的大小（4 GB 加一页的块头），两块紧挨着。
5. **栈在最高端**：`local` 在 `0x00007ffe...`，接近用户态地址空间的上沿。

> 这里不要把"堆"理解成只有一块。小对象和大对象落在不同的区域，是 `malloc` 的实现策略决定的；课件想强调的是各类数据落在哪个大区，而不是区域内的精确地址。

### 1.3 为什么要讲这个

下一节要讲的攻击需要知道"代码在哪、栈在哪"，防御手段也是围绕"让这些位置不可预测、不可执行"设计的。先有这张图，后面的内容才容易理解。

## 2. 缓冲区溢出：问题从哪里来

### 2.1 没有长度限制的库函数

C 语言的数组不带长度信息，也不做边界检查。Unix 的 `gets` 是最典型的例子：

```c
/* Get string from stdin */
char *gets(char *dest)
{
    int c = getchar();
    char *p = dest;
    while (c != EOF && c != '\n') {
        *p++ = c;
        c = getchar();
    }
    *p = '\0';
    return dest;
}
```

`gets` 只接收一个目的地址，**没有任何办法告诉它最多读多少个字符**。它会一直读到换行为止，读多少写多少。同类的问题还出现在：

- `strcpy`、`strcat`：复制任意长度的字符串；
- `scanf`、`fscanf`、`sscanf` 使用 `%s` 转换时，同样不限制长度。

当目标缓冲区比输入短时，多出来的字节就会写到缓冲区**之后**的内存里，这就是**缓冲区溢出**（buffer overflow）。

### 2.2 一个脆弱的例子

```c
/* Echo Line */
void echo()
{
    char buf[4];      /* 太小了！ */
    gets(buf);
    puts(buf);
}

void call_echo()
{
    echo();
}
```

课件的运行记录：

```
unix> ./bufdemo-nsp
Type a string:012345678901234567890123
012345678901234567890123

unix> ./bufdemo-nsp
Type a string:0123456789012345678901234
Segmentation Fault
```

`buf` 只有 4 字节，输入 24 个字符却什么事都没有，输入 25 个字符才段错误。要弄清楚原因，得看编译后的汇编和栈帧。

### 2.3 echo 的汇编与栈帧

```asm
00000000004006cf <echo>:
  4006cf: sub    $0x18,%rsp          # 分配 24 字节
  4006d3: mov    %rsp,%rdi           # buf 的地址 = %rsp，作为 gets 的参数
  4006d6: callq  400680 <gets>
  4006db: mov    %rsp,%rdi
  4006de: callq  400520 <puts@plt>
  4006e3: add    $0x18,%rsp
  4006e7: retq

00000000004006e8 <call_echo>:
  4006e8: sub    $0x8,%rsp
  4006ec: mov    $0x0,%eax
  4006f1: callq  4006cf <echo>
  4006f6: add    $0x8,%rsp          # echo 的返回地址是 0x4006f6
  4006fa: retq
```

逐步看栈：

1. `call_echo` 执行 `callq 4006cf` 时，把下一条指令的地址 `0x4006f6` 压栈，作为 `echo` 的**返回地址**，占 8 字节；
2. `echo` 一进来就 `sub $0x18,%rsp`，在栈上腾出 24 字节；
3. `buf` 就放在新的栈顶 `%rsp` 处，只用了其中最低的 4 字节，剩下 20 字节是**未使用**的（编译器为栈对齐等原因多留的空间）。

所以 `echo` 的栈帧自下（低地址）而上是：4 字节 `buf`，20 字节空闲，8 字节返回地址，一共 32 字节：

![](/obsidian-assets/f1654f85460f2eda.png)

有两件事决定了攻击的可能：

- **栈向低地址增长，而数组是向高地址写的。** `buf` 在栈帧较低处，`gets` 从 `buf[0]` 开始一路往高地址写，写过头就会经过未使用区，然后撞上返回地址。
- **返回地址是普通的内存数据。** `ret` 指令只是把栈顶 8 字节当作地址取出来跳转，它不检查这个值是不是 `call` 压进去的那一个。

### 2.4 逐字节分析：23、24、25 个字符

`gets` 在读完字符后还要写一个字符串结束符 `'\0'`。因此输入 $n$ 个字符，会写入 $n+1$ 个字节（第 0 到第 $n$ 字节）。结合上图：

- **输入 23 个字符**：写入字节 0–23，终止符落在第 23 字节，仍在未使用区内，返回地址完好，程序正常。
- **输入 24 个字符**（课件第一个例子）：写入字节 0–24，终止符 `0x00` 落在第 24 字节，即**返回地址的最低字节**。小端序下返回地址 `0x4006f6` 的字节是 `f6 06 40 00 00 00 00 00`，最低字节 `f6` 被改成 `00`，变成 `0x400600`。`echo` 执行 `ret` 时跳到 `0x400600`。这个地址恰好落在 `register_tm_clones` 里的一段无关指令中，课件显示执行过程中"可能发生了很多事"，但最后通过 `retq` 返回到了主函数，程序看起来正常。
- **输入 25 个字符**：第 24 字节被写成第 25 个字符 `'4'`（`0x34`），第 25 字节被写成 `0x00`，返回地址变成 `0x400034`。这不是合法的代码地址，`ret` 后取指令时段错误。

> 这个例子也说明，**程序"看起来正常"并不代表没有被破坏**：只要返回地址被改写，之后的行为就不可预期，有时碰巧不崩溃，有时崩溃，而对攻击者来说，最有价值的是"可控地跳到想去的地方"。

注意：具体输入多少个字符会出问题，取决于编译器为 `echo` 分配的栈帧布局（优化级别、是否使用 `%rbp` 作帧指针都会改变它），课件里的 24 与 25 只对应课件中那份汇编，不能当作定值。

## 3. 代码注入攻击

### 3.1 思路

既然返回地址可以被改写，攻击者就可以**选择**覆盖成什么。最直接的做法是：

1. 构造一个输入字符串，其中**包含一段可执行代码的机器码**（比如启动一个 shell）；
2. 字符串继续往后写，用这段代码在栈上的地址 $B$，**覆盖返回地址 $A$**；
3. 函数执行 `ret` 时，就会跳到栈上这段"注入的代码"开始执行。

![](/obsidian-assets/260d01b465df0f80.png)

图中 `Q` 里的 `buf[64]` 是缓冲区，`gets` 写入的数据依次是：注入代码（exploit code）、填充（pad）、新的返回地址 $B$（指向注入代码）。`Q` 返回时，不是回到 `P`，而是去执行了攻击者的代码，并且是以被攻击程序的权限在运行。

### 3.2 这个攻击要求什么

攻击者必须同时做到：

1. 知道**缓冲区在栈上的地址** $B$，才能把返回地址覆盖成它；
2. 栈上的数据**可以被当作代码执行**。

这两条正是后面两道系统级防线要破坏的。

### 3.3 课件里的实验

课件还安排了一个小实验（虚拟机中演示）：函数 `test` 调用 `getbuf`，要求利用溢出，让 `getbuf` 返回后**不回到 `test`，而是直接执行 `touch1`**。这类实验的做法是：用若干填充字节填满缓冲区和栈帧中返回地址之前的部分，再把 `touch1` 的地址按**小端序**写进返回地址那 8 个字节。这个例子不需要注入代码，只需要改写返回地址，是最简单的情形。

## 4. 怎么防：三道防线

课件把预防手段分为三类：写出没有漏洞的代码、系统级防护、编译器的金丝雀。

### 4.1 防线一：从源头避免漏洞

直接使用**带长度限制**的库函数：

```c
void echo()
{
    char buf[4];
    fgets(buf, 4, stdin);     /* 最多读 3 个字符，并保证以 '\0' 结尾 */
    puts(buf);
}
```

- 用 `fgets` 代替 `gets`；
- 用 `strncpy` 代替 `strcpy`；
- `scanf` 不使用无宽度的 `%s`，用 `%ns`，其中 `n` 是最大宽度。

这是最根本的办法，但也最依赖程序员，而世界上有大量历史代码。所以还需要后面的两道防线兜底。

### 4.2 防线二：系统级防护

**（1）栈随机化（ASLR，地址空间布局随机化）。**

攻击者必须知道 $B$。如果每次运行栈的位置都不同，$B$ 就无法预先算出来。做法是：程序一开始，在栈上**随机分配一段大小不定的空间**，整个栈因此被整体移动。

课件用同一个程序运行 5 次，`local` 的地址分别是：

```
0x7ffe4d3be87c   0x7fff75a4f9fc   0x7ffeadb7c80c   0x7ffeaea2fdac   0x7ffcd452017c
```

每次都不同，攻击者在不知道当次栈地址的情况下，注入代码的起始地址 $B$ 只能猜。

**（2）不可执行段（NX）。**

早期 x86 只能把内存标为"只读"或"可写"，而**可读就意味着可执行**，栈上的数据也能被当作指令执行。x86-64 增加了显式的"可执行"权限位，栈被标记为不可执行，**任何试图执行栈上代码的行为都会失败**（触发异常），这样即使攻击者把代码注入了栈并且跳了过去，也无法运行。

> 这是处理器支持的机制，由操作系统在设置页表权限时打开。

### 4.3 防线三：栈金丝雀（stack canary）

#### 原理

在缓冲区与返回地址之间放一个特殊值（canary，煤矿里用来预警的金丝雀）。**函数返回前检查这个值是否还和原来一样**：如果有人想通过溢出改写返回地址，必然要先写过 canary，它就会变化，程序发现后立刻终止，而不是继续执行 `ret`。

GCC 的对应选项是 `-fstack-protector`，现在默认打开。课件的运行记录：

```
unix> ./bufdemo-sp          unix> ./bufdemo-sp
Type a string:0123456       Type a string:01234567
0123456                     *** stack smashing detected ***
```

#### 汇编层面如何实现

```asm
echo:
  40072f: sub    $0x18,%rsp
  400733: mov    %fs:0x28,%rax          # 从 %fs:0x28 取出 canary 值
  40073c: mov    %rax,0x8(%rsp)         # 存到栈上，位于 buf 之上
  400741: xor    %eax,%eax              # 清除寄存器中的 canary 副本
  400743: mov    %rsp,%rdi
  400746: callq  4006e0 <gets>
  40074b: mov    %rsp,%rdi
  40074e: callq  400570 <puts@plt>
  400753: mov    0x8(%rsp),%rax         # 取出栈上的 canary
  400758: xor    %fs:0x28,%rax          # 与原值比较（相同则结果为 0）
  400761: je     400768 <echo+0x39>
  400763: callq  400580 <__stack_chk_fail@plt>   # 不同：报错并终止
  400768: add    $0x18,%rsp
  40076c: retq
```

有几点值得注意：

- canary 的原值保存在段寄存器 `%fs` 指向的区域内，偏移 `0x28`，在 glibc 中叫 `stack_chk_guard`，进程启动时随机生成。这个位置**不在栈里**，所以栈溢出改不了它；
- 栈上的副本放在 `0x8(%rsp)`，也就是 `buf`（`0`–`3`）之后，返回地址（`24`–`31`）之前；
- `xor %eax,%eax` 把 `%rax` 里的 canary 副本清掉，避免它在别处泄露；
- 比较用的是 `xor` 而不是 `cmp`，结果为 0 即相等，`je` 跳过 `__stack_chk_fail`。

栈帧如下（偏移从 `%rsp` 起算，单位字节）：

#### 一个细节：为什么课件里输入 8 个字符才报错

按上面的汇编，`buf` 在 `0`–`3`，canary 在 `8`–`15`，输入 $n$ 个字符会写 $n+1$ 个字节。从字节数看，输入 8 个字符写到第 8 字节，刚好碰到 canary 的最低字节。

是否会报错取决于**被写入的那个字节与 canary 原来的值是否不同**。在 x86-64 Linux 的 glibc 中，canary 的**最低字节恒为 `0x00`**（用 `buf[4]` 加 `-fstack-protector-all` 编译一个 `gets` 例子实测：输入 4 个字符，终止符落在 canary 最低字节上，不报错；输入 5 个字符才报 `stack smashing detected`）。这是 glibc 有意为之的设计：让字符串类函数写入的终止符 `'\0'` 无法"悄悄"改掉它，同时也让攻击者无法借助字符串函数把 canary 的内容完整读出来。所以在这种实现下，只多写一个终止符并不会触发检查，要再多输入一个字符才报错。课件的运行结果是 8 个字符报错，与具体运行环境和 glibc 版本有关，**不要把"8"当作定论**。理解"终止符可能正好落在 canary 的哪一个字节上"才是重点。

### 4.4 三道防线的效果小结

| 手段 | 破坏了攻击的哪一环 |
| --- | --- |
| 使用带长度限制的函数 | 从源头消除溢出 |
| 栈随机化 | 攻击者不知道注入代码的地址 $B$ |
| 不可执行栈 | 注入的代码即使被跳到也执行不了 |
| 金丝雀 | 返回前发现栈已被破坏，终止程序 |

## 5. ROP：绕过 ASLR 与 NX

### 5.1 攻击者的新处境

现在对攻击者来说，有两个困难：

- 栈位置随机，**不知道缓冲区地址**；
- 栈不可执行，**注入的代码没法运行**。

课件给出的替代策略是：**不再注入新代码，而是复用程序里已有的代码**。进程里本来就有大量可执行代码（程序自身和共享库），而且**代码段的位置每次运行是固定的**（课件的前提），攻击者可以把现有代码里的若干小片段串起来，拼出想要的功能。这就是**返回导向编程**（Return-Oriented Programming，ROP）。

> 现实中共享库地址也会被随机化，这里课件是在讨论基本思想。同时，课件也明确指出：ROP **不能对付金丝雀**，因为 canary 检查发生在 `ret` 之前，要改写返回地址还是得先覆盖 canary。

### 5.2 Gadget

**Gadget** 指一段以 `ret` 结尾的短指令序列。`ret` 的机器码是单字节 `0xc3`，所以只要有一段字节以 `c3` 结尾，从它的某个位置开始执行，到 `c3` 就会"返回"。

**例 1：取现有函数的尾部。**

```asm
00000000004004d0 <ab_plus_c>:      # long ab_plus_c(long a, long b, long c) { return a*b + c; }
  4004d0: 48 0f af fe     imul   %rsi,%rdi
  4004d4: 48 8d 04 17     lea    (%rdi,%rdx,1),%rax
  4004d8: c3              retq
```

如果从 `0x4004d4` 开始执行，就只会做 `%rax ← %rdi + %rdx`，然后 `ret`。**这个函数的尾部本身就是一个有用的 gadget**，地址是 `0x4004d4`。

**例 2：从指令中间开始解读字节。**

```asm
<setval>:            # void setval(unsigned *p) { *p = 3347663060u; }
  4004d9: c7 07 d4 48 89 c7     movl   $0xc78948d4,(%rdi)
  4004df: c3                    retq
```

x86 的指令长度不固定，同一串字节从不同位置开始读，会得到不同的指令。从 `0x4004dc` 起（也就是跳过前三个字节 `c7 07 d4`）读，字节是 `48 89 c7 c3`，对应的是：

```asm
  4004dc: 48 89 c7        movq   %rax,%rdi
  4004df: c3              retq
```

于是这个看似与寄存器无关的赋值函数里，藏着一个 `%rdi ← %rax` 的 gadget，地址是 `0x4004dc`。课件说"字节码被重新解释"就是这个意思。

### 5.3 如何把 gadget 串起来

关键在于 **`ret` 做的事就是"取出栈顶 8 字节，跳过去"**。所以如果把攻击者控制的缓冲区溢出，在栈上依次排好 gadget 的地址，那么：

1. 原函数 `ret`，取栈顶 8 字节（gadget 1 的地址），开始执行 gadget 1；
2. gadget 1 以 `ret` 结尾，此时栈顶就是 gadget 2 的地址，于是转去执行 gadget 2；
3. 如此类推，每一个 gadget 末尾的 `ret` 触发下一个 gadget。

![](/obsidian-assets/74d57c7594cddf83.png)

图中栈内从 `%rsp` 开始依次是各个 gadget 的地址，每个 gadget 代码（以 `c3` 结尾）都是程序里已有的一段，攻击者没有写入任何新的代码，写入的只是**一串地址**。栈上的这些数据被当作数据读取，不需要栈可执行；它们指向的是代码段，本来就可执行。

把上面两个例子串起来，就是最小的演示：先执行 `0x4004d4`（`%rax = %rdi + %rdx`），再执行 `0x4004dc`（`%rdi = %rax`），效果等价于 `%rdi ← %rdi + %rdx`，这是纯靠已有代码拼出来的一次计算。

> 课件只讲到这里。实际的 ROP 攻击中还需要能"把栈上的数据装进寄存器"的 gadget（比如以 `pop %rdi; ret` 结尾的片段），才能给后面的函数传入想要的参数；这里不展开。

## 6. 回头看：为什么是这三层

把整件事串起来：

1. 问题的根子在于**C 语言不检查数组边界**，加上**返回地址与局部数组同在一个栈上、且数组向高地址写、栈向低地址长**；
2. 最直接的修补是写对代码（`fgets` 等）；
3. 但代码里总有漏洞，所以系统层面提供 **ASLR**（让地址不可预测）与 **NX**（让数据区不可执行），金丝雀则从编译器层面**检测破坏**；
4. 攻击者随之转向**复用已有代码**（ROP），逼着防御者继续增加手段。这是一个攻防持续升级的过程，没有哪一层可以单独保证安全。

## 小结

1. 一个 Linux 进程的地址空间从低到高大致是：代码、数据、堆、共享库、栈。堆向高处增长，栈向低处增长；小块 `malloc` 走堆，大块 `malloc` 走 `mmap`。
2. `gets`、`strcpy`、`%s` 等不限制长度，数据会越过数组继续往高地址写。栈上局部数组之后就是保存的返回地址，**越过数组就可能改写返回地址**，而 `ret` 无条件使用它。
3. 以 `echo` 为例：`buf[4]` 之后有 20 字节未使用，再往后 8 字节是返回地址；输入的字符数加上终止符决定了写到哪里，所以 24 个字符改掉返回地址的最低字节、25 个字符把它改坏。
4. **代码注入**：把机器码和指向它的地址放进输入，让 `ret` 跳过去。依赖知道缓冲区地址、且栈可执行。
5. **三道防线**：使用带长度限制的函数；栈随机化与不可执行栈；金丝雀（`%fs:0x28` 处取值，返回前比较，不符则 `__stack_chk_fail`）。
6. **ROP**：不注入代码，而是在栈上排列已有代码片段（以 `ret`（`0xc3`）结尾的 gadget）的地址，每个 `ret` 触发下一个 gadget；它绕过了 ASLR 与 NX 所针对的"注入代码"，但仍需改写返回地址，因此仍然会被金丝雀检测到。
