# 计算机系统概论（九）：程序链接

> 本篇对应课件第九讲（课件标题为"80X86 汇编语言与 C 语言-5"）。前几讲一直在说"编译器把 C 翻译成汇编"。但一个程序往往由多个源文件组成，每个文件是被**分别**编译的，编译器看不到别的文件里的函数和全局变量的地址。把这些零散的 `.o` 文件拼成一个能运行的程序，就是链接要做的事。

## 1. 先看四个问题

课件开头给了三个文件：

```c
/* main.c */
int total = 11;                    // 全局变量：总成绩
extern void add_score(int);        // 声明外部函数
int main() {
    add_score(85);
    printf("Total: %d\n", total);
    return 0;
}

/* score.c */
int total;                         // 另一个全局变量？
void add_score(int s) { total += s; }

/* utils.c */
static int secret = 100;           // 静态全局变量
int helper() { printf("secret=%d\r\n", secret++); }
```

围绕它们有四个问题，本篇会逐个回答：

1. 改了一行代码，为什么编译器只重编一个文件？
2. 链接器为什么有时报 `undefined reference`？
3. 两个文件里都写了 `int total`，到底用的是哪一个？
4. 为什么静态链接的程序有 857 KB，动态链接的只有 22 KB？

## 2. 链接要解决什么问题

### 2.1 从源文件到可执行文件

```
main.c ──(cpp, cc1, as)──► main.o ─┐
                                   ├─► Linker (ld) ─► prog ──(loader)──► 内存中运行
sum.c  ──(cpp, cc1, as)──► sum.o  ─┘
```

对应命令：`gcc -Og -o prog main.c sum.c -static -fno-pie`。每个 `.c` 文件独立经过预处理、编译、汇编，生成一个**可重定位目标文件**（`.o`）；链接器把它们合成一个**可执行目标文件**；最后由操作系统的**加载器**（loader）把可执行文件的代码和数据复制进内存并运行。

链接可以紧跟在生成机器代码之后完成（**静态链接**），也可以推迟到程序加载时或运行时完成（**动态链接**，第 8 节）。

### 2.2 为什么需要链接

- **模块化**：一个程序可以由许多小源文件组成，而不是一个巨大的文件；通用函数可以做成库（数学库、标准 C 库）反复使用；
- **效率**：
  - 省时间：某个源文件被修改后，只需要**重新编译这一个**文件，再重新链接，不需要重编全部。这就回答了问题 1；
  - 省空间：库文件里集成了许多通用函数，而最终的可执行文件与内存映像里**只包含实际用到的**函数。

### 2.3 链接器做两件事

| 步骤 | 做什么 |
| --- | --- |
| **符号解析** | 把每一个符号**引用**与唯一的符号**定义**关联起来 |
| **重定位** | 把各个 `.o` 里相同类型的节合并成一个，给每个符号确定运行时地址，再把代码和数据里对这些符号的引用修改成这些地址 |

![](/obsidian-assets/2d3373424021580f.png)

先回顾"定位"问题，才看得出为什么需要重定位。

### 2.4 编译时能确定什么，不能确定什么

课件给了一张总表，把前面几讲的内容与本讲连起来：

| 对象 | 谁确定它的位置 | 说明 |
| --- | --- | --- |
| 局部变量（非静态） | 编译时 | 在栈里、寄存器里，或被优化掉 |
| 函数参数 | 编译时 | 通过规定的寄存器和栈传递 |
| 函数返回值 | 编译时 | `%rax`（和 `%rdx`） |
| 直接跳转 | 编译时 | 相对于 PC 的偏移 |
| 函数返回地址 | 运行时 | 存在栈顶 |
| 静态函数入口 | 编译时（与优化有关） | 相对于 PC 的偏移 |
| **全局函数入口** | **链接时** | 各模块的代码段合并后才能确定 |
| **全局变量** | **链接时** | 各模块的数据段合并后才能确定 |

编译器遇到**位置未知的目标**（别的模块里的函数、全局变量），不会猜一个地址，而是：先在指令里留下占位值，并生成一条**重定位条目**（relocation entry），告诉链接器"在把目标文件合并成可执行文件时，要怎么改这里"。

## 3. 目标文件与 ELF 格式

### 3.1 三种目标文件

| 种类 | 说明 |
| --- | --- |
| 可重定位目标文件（`.o`） | 含有一定格式的代码和数据，**可以与其他 `.o` 合并**成可执行文件；由唯一一个源文件生成 |
| 可执行文件（`a.out`） | 含有代码和数据，可以**直接装入内存运行** |
| 共享目标文件（`.so`） | 特殊的可重定位目标文件，可以在**加载时或运行时**被装入内存并动态链接；Windows 下叫 DLL |

这三者在 Linux 下都采用同一种标准二进制格式：**ELF**（Executable and Linkable Format），最早由 AT&T 的 System V Unix 采用，后来被 BSD Unix 和 Linux 广泛使用。

### 3.2 ELF 的结构

![](/obsidian-assets/eb63e3bb22ba5b2b.png)

各节的含义：

- **ELF header**：机器字长、字节序、文件类型（`.o`、可执行、`.so`）、机器类型等；
- **Segment header table**：仅可执行文件有，说明页大小、虚拟地址内存段、段大小等，供加载器使用；
- **`.text`**：机器代码；
- **`.rodata`**：只读数据，如字符串常量、`switch` 的跳转表（第五讲）；
- **`.data`**：**已初始化**的全局变量和静态变量；
- **`.bss`**：**未初始化**的全局变量和静态变量，在文件中**不占实际空间**，运行时才分配内存并清零；这是为了节省文件空间。初始化为 0 的全局变量也被 gcc 放进 `.bss`，因为 C 标准规定未初始化的全局变量、静态局部变量要被自动初始化为 0；
- **`.symtab`**：符号表，记录这个模块**定义和引用**的全局函数、全局变量（也包括静态变量）的名称、所在节和位置；
- **`.rel.text` / `.rel.data`**：重定位信息。`.rel.text` 说明 `.text` 里**哪些指令**（调用全局函数、引用全局变量的指令）要被修改、怎么修改；`.rel.data` 说明 `.data` 里哪些**指针数据**（初始化的全局变量）要修改；这些都是"写给链接器的指令"；
- **`.debug`**：调试信息（`gcc -g`）；
- **Section header table**：各节的偏移与大小。

> 在 x86-64 下，实际文件里这两节叫 `.rela.text` 与 `.rela.data`（多了一个 a：表示条目里带有显式的**加数** addend，见 5.2 节），课件按概念写成 `.rel.*`。

## 4. 符号解析

### 4.1 符号与符号表

程序里**定义**和**引用**了一系列符号（函数、全局变量、静态变量）：

```c
void swap() {...}          /* 定义符号 swap */
swap();                    /* 引用符号 swap */
int *xp = &x;              /* 定义符号 xp，引用符号 x */
```

编译器把符号定义放进 `.o` 的**符号表**。符号表是一个**结构数组**，每项含符号的名称、大小、位置等。链接器的工作就是把每个**引用**与某一个**定义**联系起来。

### 4.2 三类符号

| 类别 | 含义 | 举例 |
| --- | --- | --- |
| **全局符号** | 某模块定义，**可被其他模块引用** | 非 `static` 的函数、非 `static` 的全局变量 |
| **外部符号** | 某模块引用、但由**其他**模块定义的全局符号 | `extern` 声明的符号，如 `inter_sum` |
| **局部符号** | 某模块定义，且**仅此模块**引用 | `static` 的全局变量、`static` 函数 |

注意：这里的"局部符号"是**链接器**的概念，与 C 里"局部变量"不是一回事。非静态的局部变量在**栈或寄存器**里，链接器根本不知道它的存在；而局部**静态**变量存在 `.data` 或 `.bss`，会在符号表里出现。

### 4.3 一个例子

课件的两个文件：

```c
/* main.c */
extern int inter_sum(int x[4], int y);
int array[4] = {1,2,3,4};
static int brray[4] = {1,2,3,4};
static int intra_sum(int x[4], int y) { return x[y-1]; }
int main()
{
    int val = intra_sum(array, 3) + inter_sum(brray, 3);
    return val;
}

/* sum.c */
int inter_sum(int x[4], int y) { return x[y-1]; }
```

`main.o` 的符号表（`readelf -s`，`gcc -Og`）：

| 符号 | 在 `.symtab` 中？ | 类型 | 所在模块 | 所在节 |
| --- | --- | --- | --- | --- |
| `array` | 是 | 全局变量 | `main.o` | `.data` |
| `brray` | 是 | 静态全局变量（局部符号） | `main.o` | `.data` |
| `inter_sum` | 是 | 全局函数（外部符号，**未定义**） | 在 `sum.o` 中定义 | — |
| `intra_sum` | 是（与优化选项有关） | 静态函数（局部符号） | `main.o` | `.text` |
| `main` | 是 | 全局函数 | `main.o` | `.text` |
| `val` | **否** | 局部变量，链接器不知道 | — | — |

在 `main.o` 里，`inter_sum` 的节一栏是 `UND`（undefined）：这里**只有引用没有定义**。链接器在其他目标文件里找到它的定义（`sum.o` 的 `.text`），就把引用和定义联系起来。反过来，如果所有目标文件和库里都找不到，就报错 `undefined reference to 'inter_sum'`，这就回答了问题 2。

> 关于 `intra_sum`：开高优化级别时，编译器可能把这个小函数直接内联，那么符号表里就不会有它了，所以课件注明"与优化开关有关"。

### 4.4 局部静态变量

```c
int f() { static int x = 2; return x; }
int g() { static int x = 1; return x; }
```

两个函数里各有一个叫 `x` 的静态变量，它们是**不同**的变量，都存在 `.data` 中。编译器在符号表中为它们创建带唯一名称的局部符号，如 `x.0`、`x.1`（课件写作 `x.1`、`x.2`，具体编号取决于编译器版本）。所以"同名"不会冲突。

### 4.5 重复定义：强符号与弱符号

当多个模块都**定义**了同名的全局符号，链接器怎么办？先把符号分成两类：

- **强符号**（strong）：**函数**和**已初始化的全局变量**；
- **弱符号**（weak）：**未初始化的全局变量**。

三条规则：

1. **不允许有多个同名的强符号**，否则链接错误；
2. 有**一个**强符号和若干弱符号时，**选强符号**，对弱符号的引用都解析为那个强符号；
3. 有**多个**弱符号时，**任选其一**。

课件的例子：

```c
/* p1.c */ int foo = 5;   p1() {...}      // foo 强，p1 强
/* p2.c */ int foo;       p2() {...}      // foo 弱，p2 强
```

按规则 2，两个 `foo` 解析为**同一个变量**，就是 `p1.c` 里初值为 5 的那个。回到开头的问题 3：`main.c` 里 `int total = 11`（强），`score.c` 里 `int total;`（弱），所以两个文件操作的是**同一个** `total`，`add_score(85)` 之后 `printf` 看到的是 96。

#### 现代编译器的一个变化

上面规则 2、3 要求"未初始化的全局变量是弱符号"。**GCC 10 起，默认选项是 `-fno-common`**，未初始化的全局变量也被当作**强符号**放进 `.bss`。用上面的 `p1.c`、`p2.c` 实际编译验证：默认情况下链接报 `multiple definition of 'foo'`；加上 `-fcommon` 才得到课件的行为，程序里两个 `foo` 合并为一个。课件第 21 页提到的"`-fno-common` 开关"正是在说这个选项：开了它，规则 3 的"任选一个"就不再发生，而是直接报错或警告。所以：

- 课件所述规则是**链接器的符号解析规则**，仍然成立；
- 但要不要触发规则 2、3，取决于编译器把未初始化全局变量当作"强"还是"弱"。

如果两个文件各自写了 `int foo = 1;` 与 `int foo = 2;`，则无论编译选项如何，都是两个强符号，规则 1 报错。

#### 为什么这值得警惕

规则 2、3 会带来**悄无声息的错误**：假设 `p1.c` 里 `double x = 3.14;`，`p2.c` 里 `int x;`，规则 2 会把两者合并成一个 `double`，`p2.c` 里按 `int` 写 `x` 就会覆盖掉 `double` 的一部分，却没有任何警告。课件对全局变量的使用建议是：

- **尽量避免使用全局变量**；
- 必须用时，尽量用 `static`；
- 定义时就**初始化**；
- 引用别处的全局变量时，用 `extern` 声明。

## 5. 重定位

### 5.1 两个动作

符号解析完成后，每个符号引用都对应一个确定的定义。接着重定位分两步：

1. **合并节**：把所有输入文件里**同类**的节合并成同一类型的一个节（所有 `.text` 合为一个 `.text`，所有 `.data` 合为一个 `.data`），再给合并后的每条指令、每个全局变量分配运行时的内存地址；
2. **修补引用**：用汇编器生成的**重定位条目**，修改代码段与数据段中所有对这些符号的引用，使它们指向最终地址。

在课件的例子里，`main.o` 与 `sum.o` 合并后，`array`、`brray`、`main`、`inter_sum` 都有了固定地址。

### 5.2 看一次真实的重定位

先看链接前的 `main.o`（`objdump -dr main.o`），符号地址还不知道，指令里是占位的 0：

```asm
 e:  bf 00 00 00 00       mov    $0x0,%edi          # 要传 array 的地址
     f: R_X86_64_32       array                      # ← 重定位条目
13:  e8 e8 ff ff ff       callq  0 <intra_sum>       # 同文件的静态函数：偏移已知
...
1f:  bf 00 00 00 00       mov    $0x0,%edi          # 要传 brray 的地址
     20: R_X86_64_32      brray
29:  e8 00 00 00 00       callq  <inter_sum>         # 外部函数：偏移未知，占位 0
     2a: R_X86_64_PC32    inter_sum - 0x4            # ← 重定位条目
```

三类引用的差别很清楚：

- **同模块的静态函数** `intra_sum`：位置在同一个 `.text` 里，相对偏移 `0xffffffe8`（−0x18）编译时已知，不需要重定位条目；
- **全局变量** `array`、`brray`：要把它们的**绝对地址**填进 `mov` 的 4 字节立即数里，用 `R_X86_64_32`；
- **外部函数** `inter_sum`：`call` 的操作数是**相对于下一条指令的偏移**，用 `R_X86_64_PC32`，并带加数 −4。

链接后的 `prog`（`objdump -d prog`）：

```asm
4004e6 <main>:
4004ec:  bf 40 10 60 00     mov    $0x601040,%edi      # array 的最终地址
4004f1:  e8 e8 ff ff ff     callq  4004de <intra_sum>
4004fd:  bf 30 10 60 00     mov    $0x601030,%edi      # brray 的最终地址
400507:  e8 ca ff ff ff     callq  4004d6 <inter_sum>  # 偏移被修补成 0xffffffca
40050c:  01 d8              add    %ebx,%eax
```

### 5.3 重定位的算法

对每一个重定位条目，链接器依其类型修补：

- **绝对地址**（`R_X86_64_32`）：被修补位置 ← 符号的最终地址 + 加数；
- **PC 相对地址**（`R_X86_64_PC32`）：被修补位置 ← 符号的最终地址 + 加数 − **被修补位置自己的地址**。

用课件的数据验算 `call inter_sum`：`inter_sum` 在 `0x4004d6`，被修补的 4 个字节位于 `0x400508`（`call` 本身在 `0x400507`，操作码 `e8` 占 1 字节），加数是 −4：

$$0x4004d6 + (-4) - 0x400508 = \text{0xffffffca}$$

与 `prog` 里实际看到的 `ca ff ff ff` 一致。

![](/obsidian-assets/d41d3d1e8a6f70d5.png)

**加数 −4 是怎么来的？** CPU 执行 `call` 时，PC 已经指向**下一条指令**（`0x40050c`），而被修补的位置在指令末尾，起点比下一条指令的地址少 4。所以链接器算"目标地址 − 被修补位置"之后，要再减 4 才等价于"目标地址 − 下一条指令地址"。验算：$0x40050c + \text{0xffffffca}$（作为 32 位补码是 $-0x36$）$= 0x4004d6$。

PC 相对寻址的好处是，结果只取决于**两条指令之间的距离**，与整段代码被加载到哪里无关。这一点后面讲共享库的地址无关代码时还会用到。

> 数据方面：课件里 `brray` 在 `0x601030`、`array` 在 `0x601040`，即初始化的数据按声明顺序之外的方式排列，具体顺序由链接器决定，不要依赖。另外，不同版本 gcc 生成的重定位条目写法略有差异（例如新版把外部调用标成 `R_X86_64_PLT32`，对 `brray` 这类静态变量引用的是 `.data` 加偏移），原理相同。

### 5.4 加载：可执行文件变成进程

链接完成后，可执行文件里每个符号都有确定的地址。运行时加载器按 Segment header table 的描述，把它映射进内存（与第七讲的内存布局对应）：

- **只读代码段**（`.init`、`.text`、`.rodata`）从 `0x400000` 开始；
- **可读写数据段**（`.data`、`.bss`）紧随其后；
- 再往上是运行时堆（`malloc`，由 `brk` 指向堆顶）；
- 高处是共享库的映射区和用户栈（`%rsp` 为栈顶指针）。

## 6. 静态库

### 6.1 问题

标准库里有成千上万个常用函数（数学、I/O、内存管理、字符串……），怎么提供给程序员？

- **方案 1**：把它们都放进一个"大"目标文件，让用户每次都链进去。这样**空间与时间效率低**；
- **方案 2**：让程序员自己挑要链接的目标文件。高效，但**程序员负担重**。

### 6.2 解决：静态库（`.a` 文件）

把多个相关的可重定位目标文件打包成一个**带索引**的**存档文件**（archive），并增强链接器：**在存档里解析外部符号**；如果存档中的某个成员解决了某个外部符号，就把**这个成员**链接进可执行文件。

```
unix> ar rs libc.a atoi.o printf.o … random.o
```

存档文件可以增量更新：重新编译某个源文件，替换存档里对应的成员即可。

常见的静态库：

| 库 | 内容 | 规模 |
| --- | --- | --- |
| `libc.a`（C 标准库） | I/O、内存分配、信号处理、字符串、时间、随机数、整数运算 | 约 5 MB，1392 个目标文件 |
| `libm.a`（数学库） | 浮点运算（sin、cos、tan、log、exp、sqrt……） | 约 2 MB，401 个目标文件 |

用 `ar -t /usr/lib/libc.a` 可以列出成员，例如 `fork.o`、`fprintf.o`、`fscanf.o`。

### 6.3 与静态库链接

```
main2.c ─► main2.o ─┐
libvector.a (addvec.o, multvec.o) ─► 只取被引用的 addvec.o ─┤
libc.a (printf.o, …) ─► 只取 printf.o 及其依赖 ─┤
                                                   └─► ld ─► p2
```

链接器从左到右扫描命令行里的文件：遇到 `.o` 文件就并入，遇到 `.a` 文件就看其中有没有成员能解析当前尚未解析的外部符号，有就把那个成员并入，没有就跳过。最终的可执行文件**只包含被引用的函数所在的成员**（以及它们依赖的其他成员，如 `printf.o` 依赖的模块），这就是 2.2 节所说的"只包含实际用到的函数"。

> 这个扫描是单向的：**库要放在引用它的 `.o` 之后**。否则当链接器扫描到库时，还没有尚未解析的符号需要它，库会被整个跳过，后面引用它的 `.o` 又找不到，就报 `undefined reference`。这是实际使用中最常见的链接错误之一。

## 7. 静态链接的缺点

- 每个可执行文件都**各自包含**一份用到的库函数，磁盘上有大量重复；
- 多个程序同时运行时，**内存里**也有这些库函数的多份拷贝；
- 库有细小的更新（修一个 bug），所有用到它的程序都需要**重新链接**。

这就回答了问题 4：静态链接的程序把 `libc` 里用到的代码都打包进了自己的文件，所以体积大（课件 857 KB）；动态链接的程序只保存一个对共享库的引用，体积小（课件 22 KB）。用一个只调用 `puts` 的程序实测：静态链接约 785 KB，动态链接约 16 KB，量级与课件一致，具体数字随 glibc 版本与编译选项变化。

## 8. 共享库与地址无关代码

### 8.1 共享库

**共享库**（`.so`，Windows 下为 DLL）是一种特殊的可重定位目标文件，可以在**加载时或运行时**被装入内存、完成动态链接。同一份共享库代码在内存里**只有一份**，被多个进程共享。库更新时，只替换 `.so`，不需要重新链接使用它的程序。

由此带来一个问题：共享库被加载到哪个地址，每次、每个进程可能都不同。那库里的代码怎么访问**库里的全局变量**呢？不能在链接时就写死绝对地址。

### 8.2 地址无关代码（PIC）与 GOT

观察到一个事实：**代码段与数据段之间的相对位置是固定的**，不论整体被加载到哪里。所以代码里一条指令到数据段里某一项的"距离"也是固定的。

编译器利用这个事实：

1. 在数据段开头创建一张**全局偏移表**（GOT，Global Offset Table），每个被引用的全局变量在表里有一项；
2. 为 GOT 的每个表项生成一条重定位记录；
3. 代码里访问全局变量时，不直接用变量的地址，而是先**从 GOT 取出该变量的地址**，再通过这个地址访问；
4. 动态链接器在加载时把 GOT 各项**重定位**为变量的真实绝对地址。

这样，**代码段本身不用修改**（每个进程的 GOT 不同，指令相同），代码段可以安全地被多个进程共享。这种代码叫**地址无关代码**（Position-Independent Code，PIC），用 `gcc -fPIC -shared` 生成。

### 8.3 x86-64 下的实现

```c
int a;  int b;
void bar() { a = 1; b = 2; }
```

```asm
bar:
    pushq  %rbp
    movq   %rsp, %rbp
    movq   a@GOTPCREL(%rip), %rax     # 从 GOT 取出 a 的地址（RIP 相对寻址，距离固定）
    movl   $1, (%rax)                 # a = 1
    movq   b@GOTPCREL(%rip), %rax     # 从 GOT 取出 b 的地址
    movl   $2, (%rax)                 # b = 2
    popq   %rbp
    ret
```

x86-64 有 **`%rip` 相对寻址**，`a@GOTPCREL(%rip)` 直接定位 GOT 里的 `a` 项，这个偏移在链接时就可算出，所以实现很直接。

### 8.4 补充：x86-32 下的实现

x86-32 没有 `%rip` 相对寻址，只能先想办法**得到 PC 的值**：

```asm
00000510 <bar>:
  510: push   %ebp
  511: mov    %esp,%ebp
  513: call   538 <__x86.get_pc_thunk.ax>     # 把下一条指令的地址读入 %eax
  518: add    $0x1ae8,%eax                    # %eax = 0x518 + 0x1ae8 = 0x2000，即 GOT 的位置
  51d: mov    -0xc(%eax),%edx                 # 取 GOT 项（a 的地址）
  523: movl   $0x1,(%edx)                     # a = 1
  529: mov    -0x18(%eax),%eax                # 取 GOT 项（b 的地址）
  52f: movl   $0x2,(%eax)                     # b = 2
  ...
00000538 <__x86.get_pc_thunk.ax>:
  538: mov    (%esp),%eax                     # 返回地址就是 call 的下一条指令的地址
  53b: ret
```

这里的技巧是：`call` 会把返回地址（即下一条指令的地址）压栈，被调用的小函数把栈顶读进 `%eax` 再 `ret`，于是就"读到了当前 PC"。加上固定的偏移 `0x1ae8` 就得到 GOT 的地址。

### 8.5 `static` 与非 `static` 全局变量的定位有何不同

```c
static int a, b;
int c, d;
void bar() { a = 1; b = 2; c = 3; d = 4; }
```

```asm
bar:
    movl  $1, a(%rip)                  # 静态变量：直接 RIP 相对访问
    movl  $2, b(%rip)
    movq  c@GOTPCREL(%rip), %rax       # 非静态全局变量：经由 GOT
    movl  $3, (%rax)
    movq  d@GOTPCREL(%rip), %rax
    movl  $4, (%rax)
```

**`static` 变量只在本模块内可见**，它与代码的相对位置在链接时就固定了，直接用 `%rip` 相对寻址即可；**非 `static` 的全局变量可能被其他模块"抢占"**（在别的共享库或主程序里有同名定义，由动态链接器决定最终用哪个），所以必须经由 GOT 间接访问，让动态链接器在加载时填入最终地址。这正是第 4.2 节"全局符号与局部符号"的区别，在代码生成层面的体现。

## 小结

1. 编译器对每个 `.c` 单独编译，看不到别的模块里符号的地址。位置未知时，编译器留下占位值，并在 `.o` 里写下**重定位条目**。改一个文件只需重编这一个，再重新链接。
2. **链接器做两件事**：**符号解析**（每个引用对应唯一一个定义，找不到就 `undefined reference`）与**重定位**（合并同类节、分配地址、按重定位条目修补引用）。
3. **ELF** 是目标文件的标准格式：`.text`、`.rodata`、`.data`、`.bss`、`.symtab`、`.rel.*`、`.debug` 等；`.bss` 不占文件空间。
4. 符号分为全局、外部、局部三类；链接器只认符号，不知道栈上的局部变量；`static` 全局变量与函数是局部符号。
5. **强符号**（函数、已初始化的全局变量）与**弱符号**（未初始化的全局变量）：多个强符号报错；一强多弱选强；多弱任选一个。注意现代 GCC 默认 `-fno-common`，未初始化全局变量也算强符号。实际编程中应尽量不用全局变量，必须用时用 `static`、初始化并用 `extern` 声明。
6. 重定位：绝对引用填 `符号地址 + 加数`；PC 相对引用填 `符号地址 + 加数 − 被修补位置的地址`。课件中 `call inter_sum` 被修补成 `0xffffffca`。
7. **静态库**（`.a`）是带索引的目标文件存档，链接器只取能解析未定义符号的成员；命令行上库应放在引用它的目标文件之后。缺点是各可执行文件里各有一份拷贝，库更新要重新链接。
8. **共享库**（`.so`）在加载或运行时动态链接，内存中只有一份。库中的全局变量通过 **GOT** 间接访问，使代码段不需要被修改，成为**地址无关代码**；x86-64 用 `%rip` 相对寻址（`var@GOTPCREL(%rip)`），x86-32 要借助 `get_pc_thunk` 取得 PC。`static` 变量不需要经过 GOT。
