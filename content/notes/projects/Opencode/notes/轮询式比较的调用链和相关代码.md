# 轮询式比较的调用链和相关代码

## 调用链全景

```
Runner (llm.ts)
  │
  └─► context-epoch.ts: prepareOnce()     ← 第1层：调度层（三选一）
        │
        └─┬─► initialize()          ← 首次（无历史快照）
          │     └─► observe()       ← 内部并发加载所有 Source
          │
          ├─► reconcile()           ← 日常增量比较
          │     └─► observe()       ← 内部并发加载所有 Source
          │     └─► reconcileObservation()  ← 逐个比较
          │           └─► compare()         ← 单 Source 判断（make 闭包）
          │
          └─► replace()             ← compaction 后全量重建
                └─► observe()       ← 内部并发加载所有 Source
```

**关键**：`prepareOnce` 本身不直接调用 `observe()`。它选择 initialize / reconcile / replace 之一，由被选中的函数内部调用 `observe()` 去并发加载所有 Source。

## 第 1 层：`prepareOnce` — 调度"用哪种方式"

**文件**：`packages/core/src/session/context-epoch.ts`，`prepareOnce` 函数

```ts
const prepareOnce = Effect.fnUntraced(function* (
  db: DatabaseService,
  events: EventV2.Interface,
  context: Effect.Effect<SystemContext.SystemContext>,  // ← 这是一个 Effect，不是值！
  sessionID: SessionSchema.ID,
) {
```

**注意**：`context` 参数的类型是 `Effect<SystemContext>`——它**不是**已经加载好的值，而是一个"配方"。为什么传 Effect 而不是值？因为 `prepareOnce` 需要把它和数据库查询并发执行。
[[关于Effect-ts 中的Effect的理解]]
### 三路并发
```ts
const [value, stored, compaction] = yield* Effect.all(
  [context, find(db, sessionID), SessionHistory.latestCompaction(db, sessionID)],
  { concurrency: "unbounded" },
)
```

**这里一次性启动三个操作，谁先完成谁先返回**：

| 变量 | 来源 | 类型 | 含义 |
|------|------|------|------|
| `value` | `context` Effect 执行 → Registry 并发加载所有 Source → `combine` | `SystemContext` | **当前**所有上下文源的最新值 |
| `stored` | 查 `session_context_epoch` 表 | `Row \| undefined` | **上次**发给模型的 baseline + snapshot |
| `compaction` | 查最近一次 compaction 事件 | `{ seq } \| undefined` | 最近一次压缩的序列号 |

**这行代码就是"轮询"的起点**——它不是被动等通知，而是在 Safe Boundary 主动去"拉"当前值。

### 首次——没有历史快照

```ts
if (!stored) {
  const generation = yield* SystemContext.initialize(value)
  const baselineSeq = yield* insert(db, sessionID, generation)
  return { baseline: generation.baseline, baselineSeq }
}
```

如果数据库里没有这个 Session 的 epoch 记录，说明是**第一次 Provider Turn**。走 `initialize()`——把所有 Source 的 `baseline()` 渲染成全量文本，存入数据库，作为后续比较的基准。

### 有历史——决定 reconcile 还是 replace

```ts
const snapshot = yield* Schema.decodeUnknownEffect(SystemContext.Snapshot)(stored.snapshot)
  .pipe(Effect.mapError((error) => new ContextSnapshotDecodeError({...})))

const replacementSeq = compaction !== undefined && compaction.seq > stored.baseline_seq
  ? compaction.seq : undefined

const result = replacementSeq
  ? yield* SystemContext.replace(value, snapshot)   // compaction 后 → 全量重建
  : yield* SystemContext.reconcile(value, snapshot)  // 日常 → 增量比较
```

#### 代码详解
+ 好，这段代码是 `prepareOnce` 的**决策核心**——它决定用"增量比较"还是"全量重建"来处理上下文。
+ ## 从数据库恢复快照
```ts
const snapshot = yield* Schema.decodeUnknownEffect(SystemContext.Snapshot)(stored.snapshot)
  .pipe(Effect.mapError((error) => new ContextSnapshotDecodeError({...})))
```
+ 逐层拆开：
+ ### `stored.snapshot` 是什么？
+ 它是数据库 `session_context_epoch` 表里存的一行 JSON 文本。比如：
```json
{
  "core/environment": { "value": "\"<env>\\n  Working directory: /project\\n</env>\"" },
  "core/date":        { "value": "\"Jul 07 2026\"" }
}
```
+ Drizzle 在读出时自动执行 `JSON.parse`，返回已解析的 JS 对象；随后 Effect Schema 验证结构。
+ ### `SystemContext.Snapshot` 是什么？
+ 在 `packages/core/src/system-context/index.ts` 中定义：
```ts
export const Snapshot = Schema.Record(Key, SourceSnapshot)
export type Snapshot = Readonly<Record<string, SourceSnapshot>>
```
+ 这是一个 Effect Schema——它描述了"合法的 Snapshot 长什么样"：
	- 外层：`Record<Key, SourceSnapshot>`——一个字典，key 是 `"core/date"` 这种字符串
	- 内层：`SourceSnapshot`——`{ value: Json, removed?: string }`

+ ### `Schema.decodeUnknownEffect(Snapshot)(stored.snapshot)` 在干什么？
	+ `stored.snapshot` 已经是 JS 对象（Drizzle `mode: "json"` 已解析），但我们需要确认它的结构符合 `Snapshot` 类型。
```
Drizzle 已解析的 JS 对象（如 { "core/date": { value: '"Jul 07 2026"' } }）
        │
        ▼  Schema.decodeUnknownEffect(Snapshot) → 结构验证
        │
{ "core/date": { value: '"Jul 07 2026"' } }
 类型: Snapshot (Record<string, SourceSnapshot>)
```
+ **Drizzle 已完成 JSON.parse**：`text({ mode: "json" })` 已把数据库文本转换成了 JS 对象。`Schema.decodeUnknownEffect(Snapshot)` 接收到的已经是一个解析好的值，它只做结构验证——检查 key 格式是否合法、value 里是否有 `value` 字段等。
+ 如果 JSON 解析失败或者结构不对 → Effect 以 `ParseError` 失败。
+ ### `.pipe(Effect.mapError(...))` 在干什么？
```ts
.pipe(Effect.mapError((error) => new ContextSnapshotDecodeError({...})))
```
+ Schema 解码失败时，Effect 携带的错误是 `ParseError`——这是一个通用错误，调用方不知道"哪个 Session 的快照坏了"。
+ `mapError` 把通用错误**转换成业务错误**：
```ts
// 定义在 session/error.ts
export class ContextSnapshotDecodeError extends Schema.TaggedErrorClass<...>()(
  "ContextSnapshotDecodeError",
  { sessionID: SessionSchema.ID, details: Schema.String }
) {}
```
+ 这样上层调用方可以精确匹配 `ContextSnapshotDecodeError`，知道是"某个 Session 的快照数据损坏了"，而不是一个模糊的"解析失败"。
+ ### `yield*` 在干什么？
+ `yield*` 是 Effect.gen 的语法——**执行这个 Effect 并拿到结果**。
```ts
// decodeUnknownEffect 返回 Effect<Snapshot, ParseError>
// yield* 执行它 → 成功拿到 Snapshot 对象 → 赋给 snapshot 变量
//               → 失败则整个 prepareOnce 以 ContextSnapshotDecodeError 失败
const snapshot: Snapshot = yield* Schema.decodeUnknownEffect(Snapshot)(stored.snapshot)
    .pipe(Effect.mapError(...))
```
+ ## 决定是否需要重建
```ts
const replacementSeq = compaction !== undefined && compaction.seq > stored.baseline_seq
  ? compaction.seq : undefined
```
+ 这一行的核心问题是：**自从上次发 baseline 给模型之后，对话有没有被压缩过？**
+ ### 三个变量的含义

| 变量 | 来源 | 含义 |
|------|------|------|
| `stored.baseline_seq` | `session_context_epoch` 表 | **上次写入 epoch 时**，消息表中的最新序列号——用于后续历史消息过滤（见下文"历史选择"） |
| `compaction` | 查 compaction 事件 | **最近一次压缩**发生时的消息序列号，没有压缩过就是 `undefined` |
| `compaction.seq > stored.baseline_seq` | 比较 | 压缩是不是在 baseline 之后发生的？ |
+ ### 场景分析
+ **场景 1：没有压缩过**
```
compaction = undefined
→ replacementSeq = undefined
→ 走 reconcile（增量比较）
```
+ **场景 2：压缩发生在 baseline 之前**
```
baseline 写入时: seq=100
compaction 发生: seq=50
→ 50 > 100 = false
→ replacementSeq = undefined
→ 走 reconcile
```
+ 压缩比 baseline 早——说明 baseline 写入时已经**包含了压缩后的状态**，不需要重建。
+ **场景 3：压缩发生在 baseline 之后（这是关键情况！）**
```
baseline 写入时: seq=42 ──────── 在消息序列号 42 时写入了 epoch 记录
compaction 发生: seq=87 ──────── 消息序列号 87 时压缩了对话

→ 87 > 42 = true
→ replacementSeq = 87
→ 走 replace（全量重建）
```
+ 为什么必须重建？因为 compaction 把消息 1-87 的对话**压缩成了一段摘要**。原来的 `baseline_seq = 42` 作为历史过滤的基准不再有意义——压缩后消息 1-86 已被摘要替代，但 epoch 记录里的 baseline 文本还是旧世界状态渲染的。必须重建整个 baseline。
+ ### `baselineSeq` 的真正作用：历史消息过滤

`baselineSeq` 不只是"记录时间点"，它在 `history.ts` 的 `messageRows()` 中有实际用途——决定哪些消息需要发给模型。理解这个才能真正理解 Epoch 的完整语义。

**文件**：`packages/core/src/session/history.ts`，`messageRows` 函数

```ts
const messageRows = Effect.fnUntraced(function* (
  db, sessionID, compaction, baselineSeq?,
) {
  const rows = yield* db.select().from(SessionMessageTable).where(
    and(
      eq(SessionMessageTable.session_id, sessionID),
      compaction
        ? or(
            gte(SessionMessageTable.seq, compaction.seq),
            baselineSeq === undefined
              ? undefined
              : and(eq(SessionMessageTable.type, "system"), gt(SessionMessageTable.seq, baselineSeq)),
          )
        : undefined,
      baselineSeq === undefined
        ? undefined
        : or(ne(SessionMessageTable.type, "system"), gt(SessionMessageTable.seq, baselineSeq)),
    ),
  ).orderBy(asc(SessionMessageTable.seq)).all()
})
```

这段 WHERE 包含**两个独立的过滤条件**（用 `and` 连接），对应两种场景：

#### 情况 A：无 compaction（日常 Provider Turn）

```sql
-- baselineSeq 过滤（compaction 子句为 undefined，被跳过）
WHERE session_id = ?
  AND (type != 'system' OR seq > baselineSeq)
```

- **保留所有非 system 消息**（user/assistant/tool）——无条件保留，因为它们是对话本体
- **保留 seq > baselineSeq 的所有消息**（包括 system 消息）——因为 baseline 是在 baselineSeq 之后发出的，模型需要看到后续的上下文更新

换句话说：baseline 发出去时的消息（seq ≤ baselineSeq 的 user/assistant/tool）已经构成了 baseline 的"上下文世界"，不需要重复发送；但**之后**的所有消息（包括更新的 system message）必须发给模型。

#### 情况 B：有 compaction（压缩后的 Provider Turn）

```sql
-- compaction 子句 + baselineSeq 子句同时生效
WHERE session_id = ?
  AND (seq >= compaction.seq
       OR (type = 'system' AND seq > baselineSeq))
  AND (type != 'system' OR seq > baselineSeq)
```

- **`seq >= compaction.seq`**：压缩点及之后的消息全部保留——因为压缩后的摘要取代了旧消息，这些都是"新世界"
- **`type = 'system' AND seq > baselineSeq`**：compaction 之前的 system 消息也保留——那些是 baseline 之后的上下文更新（mid-conversation system messages），模型需要知道它们
- **`type != 'system' OR seq > baselineSeq`**：非 system 消息无条件保留，所有 seq > baselineSeq 的消息都保留

这样两条子句叠加的结果是：从 baseline 到 compaction 之间的**普通对话消息**被过滤掉了（已被摘要替代），但**system 消息**（上下文变化通知）被保留了下来。

#### 完整的消息过滤示意

```
消息序列:  1...40  41  42  43...86  87  88...N
                          │          │
                    baseline_seq=42   compaction.seq=87

无 compaction：
  ├─ seq≤42 的 non-system → 保留（它们是 baseline 的"上下文世界"）*
  ├─ seq≤42 的 system     → 过滤（baseline 文本已包含其信息）
  ├─ seq>42 的 non-system → 保留
  └─ seq>42 的 system     → 保留（ctx-update 必须跟上）

有 compaction（seq=87）：
  ├─ seq<87 的 non-system  → 过滤（被摘要替代）
  ├─ seq<87 且 seq>42 的 system → 保留！（baseline 后的 ctx-update 不能丢）
  ├─ seq<87 且 seq≤42 的 system → 过滤（baseline 已包含）
  └─ seq≥87 的所有消息       → 保留
```

> *注：实际发给模型时，Runner 用 `entriesForRunner` 取消息列表，其内部调用 `messageRows(db, sessionID, yield* latestCompaction(db, sessionID), baselineSeq)` 获取原始行、再解码为 `{ seq, message }` 条目。过滤后的消息列表加上 baseline system prompt 构成完整请求。

+ ## 分支执行
```ts
const result = replacementSeq
  ? yield* SystemContext.replace(value, snapshot)   // 全量重建
  : yield* SystemContext.reconcile(value, snapshot)  // 增量比较
```

| 条件                             | 走哪个函数                        | 做什么                              | 产出                                                       |
| ------------------------------ | ---------------------------- | -------------------------------- | -------------------------------------------------------- |
| `replacementSeq` 有值            | `replace(value, snapshot)`   | 所有 Source 重新 `baseline()`，生成全新文本 | `ReplacementReady { generation }` 或 `ReplacementBlocked` |
| `replacementSeq` 是 `undefined` | `reconcile(value, snapshot)` | 逐个比较 Source，只收集变化的部分             | `Unchanged` / `Updated { text }` / `Replace`             |
+ ## 这两步的设计意图：缓存友好的分界
```
═══════════ Context Epoch #1 ═══════════
baseline_seq = 42

  Provider Turn #1: reconcile → Unchanged (baseline 复用)
  Provider Turn #2: reconcile → Updated (发一条 system message)
  Provider Turn #3: reconcile → Unchanged
  ...
  Provider Turn #N: 对话太长 → compaction (seq=87)

═══════════ Context Epoch #2 ═══════════
baseline_seq = 87（replace 后重新写入）

  Provider Turn #1: reconcile → Unchanged (新 baseline 复用)
  ...
```
+ **关键**：如果没有 compaction 感知（即没有 `compaction.seq > stored.baseline_seq` 这个判断），Epoch #2 会继续用 Epoch #1 的 baseline 文本——但那个 baseline 是在消息 seq=42 时渲染的，而消息 1-86 已经被压缩掉了。`replacementSeq` 就是这个**分界标记**——"对不起，对话世界已经变了，你得重新渲染 baseline"。
+ **关键判断**：`compaction.seq > stored.baseline_seq`
	- `stored.baseline_seq`：上次写入 epoch 时的消息序列号
	- 如果 compaction 发生在这个序列号**之后**，说明对话已被压缩过，需要重建 baseline
	- 否则走日常的 `reconcile`——增量比较

### 处理三种结果

```ts
// ══════════ 出口 2：没变化 或 暂时不能换 ══════════
if (result._tag === "Unchanged" || result._tag === "ReplacementBlocked") {
  return { baseline: stored.baseline, baselineSeq: stored.baseline_seq }
  // ↑ Unchanged → 用旧 baseline（缓存友好！）
  // ↑ ReplacementBlocked → 先不换，等下次
}
// ══════════ 出口 3：全量重建 ══════════
if (result._tag === "ReplacementReady") {
  const baselineSeq = replacementSeq ?? (yield* EventV2.latestSequence(db, sessionID))
  yield* replace(db, sessionID, baselineSeq, result.generation)
  return { baseline: result.generation.baseline, baselineSeq }
}

// Updated 分支：（即增量更新）
yield* events.publish(
  SessionEvent.ContextUpdated,
  { sessionID, messageID, timestamp, text: result.text },
  { commit: () => advance(db, sessionID, result.snapshot).pipe(Effect.orDie) },
)
return { baseline: stored.baseline, baselineSeq: stored.baseline_seq }
// ↑ baseline 不变！只是追加一条 system message
```

## 第 2 层：`observe` — 并发加载所有 Source

**文件**：`packages/core/src/system-context/index.ts`，私有 `const observe`

[[observe代码详解]]
```ts
const observe = (value: SystemContext) =>
  Effect.forEach(
    value[ContextTypeId],          // PackedSource[]
    (source) =>
      source.load.pipe(            // 每个 Source 的 load Effect
        Effect.map((result): Entry =>
          result === unavailable
            ? { _tag: "Unavailable", key: source.key }
            : { _tag: "Available", key: source.key, ...result },
        ),
      ),
    { concurrency: "unbounded" },  // ← 所有 Source 并发加载
  )
```

**关键**：`{ concurrency: "unbounded" }`——所有 Source 的 `load()` 以**无界并发 fiber** 启动。在单线程 JS 运行时上，Effect 通过协作式调度交错推进各个 fiber：I/O 等待（读系统时钟、读文件系统 AGENTS.md、查 agent 配置）可在墙钟时间上重叠，但 CPU 执行并非 literal 同时进行。核心语义是"互不阻塞"——任意一个 Source 的 I/O 不会串行等待另一个先完成。

返回的是 `Entry[]`——每个元素要么是 `AvailableEntry`（带 `baseline()` 和 `compare()` 闭包），要么是 `UnavailableEntry`（只带 key）。

## 第 3 层：`reconcile` — 入口 + 路由

**文件**：`packages/core/src/system-context/index.ts`，`reconcile` 函数

先看它操作的类型：

```ts
// ── observe 并发加载后的产出 ──
type Entry = AvailableEntry | UnavailableEntry

interface AvailableEntry extends Loaded {
  _tag: "Available"
  key: Key                 // 如 "core/date"
  baseline: () => Rendered // 渲染完整 baseline
  compare: (previous: Json) => Compared  // 与旧快照比较
}
interface UnavailableEntry {
  _tag: "Unavailable"
  key: Key
}

// ── compare() 的三种可能 ──
type Compared =
  | { _tag: "Incompatible" }                           // schema 变了，旧 JSON 解不出来
  | { _tag: "Unchanged" }                              // 值等价，没变
  | { _tag: "Updated"; render: () => Rendered }        // 变了，带惰性渲染闭包

// ── reconcile 的最终返回 ──
type ReconcileResult = Unchanged | Updated | ReplacementResult
// ReplacementResult = ReplacementReady | ReplacementBlocked
```

再看函数本身：

```ts
export function reconcile(
  value: SystemContext,
  previous: Snapshot,   // Record<Key, { value: Json, removed?: string }>
): Effect.Effect<ReconcileResult> {
  return observe(value).pipe(          // ① 并发加载所有 Source，得到 Entry[]
    Effect.map((entries): ReconcileResult => {
      const result = reconcileObservation(entries, previous)  // ② 尝试增量比较
      if (result._tag === "Unchanged" || result._tag === "Updated") return result  // ③ 直接返回
      return replaceObservation(entries, previous)  // ④ 降级到全量重建
    }),
  )
}
```

| 步骤 | 做了什么 | 为什么 |
|---|---|---|
| ① `observe(value)` | 并发加载所有 Source，产出 `Entry[]` | 必须先拿到本次的真实值才能比较 |
| ② `reconcileObservation(...)` | 尝试**增量比较**：逐 key 对比新旧值 | 增量的最优路径——只需发送变化部分 |
| ③ 直接返回 | 若为 `Unchanged` 或 `Updated`，不升级 | 这就是希望的结局 |
| ④ 降级到 `replaceObservation` | reconcileObservation 返回了 `Replace` | schema 不兼容 / 缺少 removal text → "修不了，重来" |

`reconcile` 最终只有两条路：
- **增量路径**：`Unchanged`（什么都不发）或 `Updated`（只发变化文本）
- **全量路径**：退到 `replaceObservation`，要么 `ReplacementReady`（重建 baseline），要么 `ReplacementBlocked`（有之前承认的 Source 不可用了，阻塞）

---

## 第 4 层：`reconcileObservation` — 逐个比较（核心逻辑）

**文件**：`packages/core/src/system-context/index.ts`，`reconcileObservation` 函数

这是整个轮询式比较的核心实现。它不是一个简单的循环，而是**五个阶段**的有序流水线。

### 阶段 1：对 "有旧值的 Available entry" 做 compare

```ts
const keys = new Set(entries.map((entry) => entry.key))
const comparisons = new Map<Key, Compared>()

for (const entry of entries) {
  if (entry._tag === "Unavailable") continue      // 不可用——跳过后由阶段 3 处理
  const stored = getSnapshot(previous, entry.key)  // 查 snapshot 里有没有旧值
  if (!stored) continue                            // 新出现的 key——跳过后由阶段 3 处理
  const compared = entry.compare(stored.value)      // ← 调 codec 做等价比较
  if (compared._tag === "Incompatible") return { _tag: "Replace" }  // 快失败
  comparisons.set(entry.key, compared)
}
```

**做了三件事**：

1. **建立 key 集合**——`keys = Set(entries.map(e => e.key))`，后面阶段 2 和阶段 4 用。
2. **跳过的**：`Unavailable` entry（无法加载，不知道值，谈不上比较），以及新出现的 key（previous 里不存在，没有"旧值"可比较）。
3. **需要比较的**：当前是 `Available` **且** previous 有旧值。调用 `entry.compare(stored.value)`——这是 `make()` 里基于 codec 创建的闭包：先把旧 JSON **解码**为 `A` 类型，再用 `Schema.toEquivalence` 判断新旧值是否**等价**。
4. **快速失败**：如果某个 key 的旧 JSON 解不出来（codec 改了），`compare` 返回 `Incompatible`，立即返回 `Replace`——通知外层走全量重建。

> **为什么"阶段 1 先跑完再进阶段 3"？**
> 因为阶段 1 可能的快速失败（`Incompatible → Replace`）应该尽早触发，避免在阶段 3 里对剩余 entry 做了无用功。这是一个"先验、再动工"的设计。

### 阶段 2：检查 previous 里有但 current 里没有的 key

```ts
for (const key of Object.keys(previous).sort()) {
  if (keys.has(Key.make(key))) continue           // current 里有——不关心
  if (previous[key].removed === undefined) return { _tag: "Replace" }
}
```

遍历 previous snapshot 的 key，找**被整体移除的 Source**。比如 `core/instructions` 这个 Source 在之前的轮次里参与了 System Context，但现在 AGENTS.md 文件被删了，`InstructionContext` 返回了 `SystemContext.empty`，这个 key 就从当前 entries 里消失了。

如果 missing key 的 snapshot 里**没有**预渲染的 `removed` 文本（意味着当初这个 Source 没定义 `removed` 回调），那就无法增量告知模型"某上下文不再适用"——返回 `Replace`，走全量重建。

### 阶段 3：构建新 snapshot + 收集增量文本

这是**增量渲染的核心**。对每个 entry，分四种情况：

```ts
const snapshot: Record<string, SourceSnapshot> = {}
const updates: string[] = []

for (const entry of entries) {
  const stored = getSnapshot(previous, entry.key)
```

然后进入分支：

**情况 A：Unavailable**

```ts
  if (entry._tag === "Unavailable") {
    if (stored) snapshot[entry.key] = stored   // stale-while-revalidate
    continue                                   // 不产出增量文本
  }
```

不可用的 Source：如果 previous 有旧 snapshot，保留（`stale-while-revalidate`）；**不**产出增量文本。上游会判断"没变化"，沿用旧 baseline 里的文本。

**情况 B：新出现的 Available entry**

```ts
  if (!stored) {
    const rendered = entry.baseline()          // 渲染完整 baseline
    updates.push(rendered.text)                // 作为增量文本加入
    snapshot[entry.key] = rendered.snapshot    // 写入新 snapshot
    continue
  }
```

previous 里不存在的 key——新增的 Source（比如新注册了一个 `core/foo`）。调用 `baseline()` 生成初始文本，当作增量内容。

**情况 C1：Unchanged**

```ts
  const compared = comparisons.get(entry.key)
  if (compared._tag === "Unchanged") {
    snapshot[entry.key] = stored              // 原样保留旧 snapshot
    continue                                   // 不产出增量文本
  }
```

没变。snapshot 留旧值，不产出文本。

**情况 C2：Updated**

```ts
  const rendered = compared.render()          // ← 惰性求值！只有确认"变了"才调用
  updates.push(rendered.text)
  snapshot[entry.key] = rendered.snapshot
```

变了。调用 `compared.render()`——这是 `compare()` 里包裹的**惰性闭包**，只有走到这行才会真正调用 `source.update(previous, current)` 渲染文本。这是性能关键：如果没变，`update()` 永远不会被执行。

### 阶段 4：追加被移除 Source 的 removal text

```ts
for (const key of Object.keys(previous).sort()) {
  if (keys.has(Key.make(key))) continue
  const removed = previous[key].removed      // 从 old snapshot 中取预渲染文本
  updates.push(removed)
}
```

再次遍历 previous snapshot 里被移除的 key（阶段 2 已经验证过 `removed` 存在，这里不会抛错），将预渲染的 removal text 追加到增量消息中。这样模型就知道"AGENTS.md 已不再适用"之类的上下文变更。

### 阶段 5：根据结果返回

```ts
if (updates.length === 0) return { _tag: "Unchanged" }
return { _tag: "Updated", text: render(updates), snapshot }
```

`render(updates)` 只是 `parts.join("\n\n")`（私有 `render` 函数）。

| 结果 | 语义 | Runner 后续行为 |
|---|---|---|
| `Unchanged` | 所有 Source 的值和 snapshot 一致 | 直接复用旧 baseline；无 system message |
| `Updated` | 至少一个 Source 的值变了 | `text` 会被 `prepareOnce` → `ContextUpdated` 事件发布为 Mid-Conversation System Message |
| `Replace` | 阶段 1 或阶段 2 的短路 | `reconcile` 降级到 `replaceObservation`——要么重建 baseline，要么阻塞 |

### 为什么阶段 1 和阶段 3 不合并成一个循环？

阶段 1 只做"比较"，不修改任何状态。它有两个用途：

1. **快速失败**：`Incompatible` 一旦出现，立即返回 `Replace`，阶段 3 的 snapshot 构建完全不做。
2. **分离关注点**：阶段 1 回答"哪些变/不变/不兼容"，阶段 3 回答"怎么为每个 entry 生成文本和 snapshot"。两个问题不同，合并到同一循环会让代码失去这种清晰的结构——你能一眼看到"这里可能会提前短路"，而不是在一大段分支里找 exit 点。

### 五个分支的完整汇总

| 情况 | entry._tag | previous 有值? | compare 结果 | snapshot | 增量文本 |
|---|---|---|---|---|---|
| 不可用 | `"Unavailable"` | — | — | 保留旧值（stale-while-revalidate） | 无 |
| 新增 | `"Available"` | 无 | — | `baseline()` → 新 snapshot | `baseline()` 文本 |
| 没变 | `"Available"` | 有 | `Unchanged` | 保留旧值 | 无 |
| 变了 | `"Available"` | 有 | `Updated` | `update()` → 新 snapshot | `update()` 文本 |
| 被移除 | （不在 entries 中） | 有 | — | 不存 | `removed` 预渲染文本 |

## 完整调用时序

```
Safe Provider-Turn Boundary 到达
  │
  ├─ prepareOnce()
  │   ├─ Effect.all → 并发: context加载 + DB查询 + compaction查询
  │   ├─ 首次 → SystemContext.initialize() → 全新 baseline
  │   ├─ compaction后 → SystemContext.replace() → 新 baseline
  │   └─ 日常 → SystemContext.reconcile(value, snapshot)
  │
  └─ reconcile(value, snapshot)
      ├─ observe(value) → 并发执行所有 Source.load()
      └─ reconcileObservation(entries, snapshot)
          ├─ 遍历 entries，调用 entry.compare(stored.value)
          │         └─ 回到 make() 闭包: decode→equivalent→Unchanged/Updated/Incompatible
          ├─ Incompatible → 短路返回 Replace
          ├─ 检测被移除的 Source（无 removed → Replace）
          ├─ 第二轮遍历，收集 updates[] + 构建新 snapshot
          └─ 有更新 → Updated | 无更新 → Unchanged
```

---

## 总结：为什么叫"轮询式"

整个机制没有一行 `addEventListener`、没有 `EventEmitter`、没有 `watch`。它就是一个函数调用链：

1. **Safe Boundary 到了** → Runner 主动调用 `ContextEpoch.prepare()`
2. `prepareOnce` **主动并发加载**所有 Source 的当前值 + 数据库里的上次快照
3. `reconcileObservation` **逐个调用**每个 Source 的 `compare()` 闭包
4. 闭包内部用 `decode → equivalent` 判断变没变
5. 返回结果，Runner 决定是复用旧 baseline 还是发送 system message
